# WP-104 part c: spec problems and proposals

Each item: the spec line, what I observed, what I wrote in `rules/`, and the change I propose.

1. **`google-tags.json` `gcd` cannot be "generated from Google's Consent Mode documentation": Google publishes no `gcd` table, and the shape cannot express most letters.**
   - Spec: `privacy.md` § 1: "`gcd`: `[{ pattern, default: { ad_storage: "granted"|"denied", … }, update: { same keys } }]` … Rows are generated by WP-104 from Google's Consent Mode documentation."
   - Observed: Google's consent-mode page (`developers.google.com/tag-platform/security/concepts/consent-mode`, fetched 2026-10-22) says only that "The gcd parameter is always sent to Google services, regardless of whether consent mode is activated or not" and gives no letter table. The decoding exists only in vendor documentation that reverse-engineers it: CookieHub (`docs.cookiehub.com/advanced/consent-mode-v2-signals`) and UniConsent (`uniconsent.com/consent-data-validator`), which agree. Format: `1<N><ad_storage><N><analytics_storage><N><ad_user_data><N><ad_personalization><end digit>`; letters `l` (no signal), `m` (no default, update denied), `n` (no default, update granted), `p` (default denied, no update), `q` (denied, denied), `r` (denied, granted), `t` (default granted, no update), `u` (granted, denied), `v` (granted, granted). A letter can therefore mean "no default" or "no update", which `"granted"|"denied"` cannot say.
   - Wrote: `rules/google-tags.json` keeps the spec keys (`hosts`, `libraryPaths`, `measurementPaths`, `gcd`) and adds `gcdLetters` (`{ "<letter>": { default, update } }` with `null` for "not set"). `gcd` has 81 rows, one per combination of per-signal DEFAULT state (`denied` = `[pqr]`, `granted` = `[tuv]`, none = `[lmn]`), anchored on the whole value (`^1\d+[pqr]\d+…\d+$`, so the separators and the end digit may be any digits). `default` is exact (the rows are disjoint and each string matches exactly one; `wp/WP-104/scripts/part-c-check-gcd.mjs` checks all 6561 letter combinations); `update` is `null` for every key, because the update state differs per letter inside a row. PRV-011 reads only `default` ("denied-by-default for all four types" = the row whose four defaults are `denied`), so nothing in the spec is lost.
   - Proposal: state in § 1 that `default`/`update` values may be `null` (not set), that rows are keyed by default-state class, that `update` is read from `gcdLetters`, and that the table is derived from vendor documentation because Google publishes none (a drift risk: a quarterly `fetch` refresh against a live Google tag capture is advisable). WP-206's loader must accept `null`.

2. **`regulated-product-regimes.json` shape is `[{ id, categoryRegexes: { locale: [regex] } }]` but the regex dialect and flags are unstated.** I wrote Rust `regex` syntax (compiled and tested with regex 1.13.1), inline `(?i)` on every regex, `\b` word boundaries for space-delimited scripts and plain substrings for compound-word languages (de nl da sv nb fi) and for scripts without spaces. Proposal: say "Rust `regex` syntax, matched case-insensitively; the file's regexes carry their own `(?i)`".

3. **`unit-quantity-patterns.json` `perRegex` cannot cover the German/French/Italian form "1 kg = 12,50 €" (price after the unit).** One regex cannot capture `price`, `n` and `unit` in both orders (Rust `regex` rejects duplicate group names and has no branch reset). I wrote the price-first form (`12,50 €/kg`, `12,50 € pro kg`, `€3.50 per 100 ml`, `250円/100g`). Proposal: allow `perRegex` to be an array of regexes tried in order, or add `perRegexAlt`. Also unstated: `units[].symbol` is compared case-folded (I write them lower case), and the `price` group is the text handed to the 04 § 11 parse-back (so it includes the currency symbol or code).

4. **`required-legal-pages.json`: BUILD_MAP names `kr-pipa`, `cn-pipl`, `br-lgpd`, `ca-pipeda`, `jp-appi` as requiring legal pages, but not which key.** I wrote `privacy` for each (and for `au-privacy`, `in-dpdp`, `us-state-privacy`). `us-tcpa` → `privacy` + `terms` (PRV-032 links to both and says a missing key is PRV-022's). Please confirm.

5. **`market-signals.json`: `.eu` and `EU`.** The shape keys `regions` by ISO 3166-1 alpha-2 and `tlds` map to those codes. `.eu` is a ccTLD with no country. I added `tlds.eu = "EU"` and `regions.EU = ["eu-gdpr"]` (EU is an exceptionally reserved alpha-2 code). Drop the two entries if the spec's matcher must only see assigned codes. I also added the non-euro EU/EEA currencies (BGN, CZK, DKK, HUF, PLN, RON, SEK, ISK, NOK) to `currencies`: the spec says "EUR → eu-gdpr … likewise" and names only the euro; a price in SEK is as clear a signal.

6. **`consent-models.json`: the spec lists the jurisdictions but defines "opt-out" only implicitly.** I read "opt-out" as "the regime does not require consent before non-essential cookies". `opt-out`: `us-ca-ccpa`, `us-state-privacy`, `au-privacy`, and the sector regimes that do not govern cookies at all (`us-consumer`, `us-ca-prop65`, `us-tcpa`, `us-ugc`, `uk-consumer`, `uk-osa`, `au-consumer`, `au-spam`, `br-consumer`, `ca-consumer`, `ca-casl`, `in-ecommerce`, `kr-ecommerce`, `jp-sct`, `cn-icp`, `eu-eaa`, `eu-dsa`). `opt-in`: `eu-gdpr`, `uk-gdpr`, `de`, `at`, `eu-consumer`, `kr-pipa`, `cn-pipl`, `br-lgpd`, `ca-pipeda`, `ca-qc`, `jp-appi`, `in-dpdp`. CFG-006 accepts `consent.required: false` only when every declared jurisdiction is `opt-out`, so a wrong `opt-out` weakens the gate: counsel should review the `au-privacy` entry (the Privacy Act has no cookie-consent rule) and the `ca-pipeda` and `jp-appi` entries I kept `opt-in` on purpose.

7. **`provider-id-by-country.json`: `placeNames` keys.** The spec gives `GB-ENG` → "England and Wales". `legal.registerCountry` may also be `GB`, `GB-WLS`, `GB-SCT`, `GB-NIR`; I wrote entries for all five (SI 2015/17 reg. 25(2)(a): "the part of the United Kingdom in which the company is registered"). A `registerCountry` of `GB-ENG` accepts only "England and Wales"; `GB-WLS` accepts "Wales" or "England and Wales"; `GB` accepts any of the four.

8. **`google-certified-cmps.json`: the CMP list and the version floor will go stale.** Google updates its table weekly; I recorded the 124 web-capable ids on 2026-10-22 and `minTcfPolicyVersion: 5` (the live GVL's `tcfPolicyVersion`; TCF v2.3 is mandatory for Google ad requests since 2026-03-01). Proposal: mark both files in `rules/provenance.json` as refreshed by `fetch` (as is done for the Public Suffix List) rather than frozen per ruleset release.

9. **`tcf-ad-vendors.json`: only three hosts could be sourced.** Google's own guides name `pagead2.googlesyndication.com` (AdSense and the Google tag), `securepubads.g.doubleclick.net` (Ad Manager GPT) and `googleads.g.doubleclick.net`. The spec's "AdSense, Ad Manager, …" suggests more; any further host needs a Google source (not invented). All three share GVL vendor 755 ("Google Advertising Products", verified in GVL v181).

10. **PRV-030 (FR, IT) legal texts could not be fetched.** Légifrance answered 403 to scripts; I did not fetch the Italian Codice civile art. 2250. FR/IT entries follow the spec text. NL (BW 3:15d), ES (LSSI art. 10) and GB (SI 2015/17 reg. 25) were read from the legal text.

11. **PRV-021 `withdrawal-labels` for Norway (`nb`).** The EEA has not yet incorporated Directive (EU) 2023/2673 into Norwegian law as far as I could find (search only; `angrerettloven` § 16(2) has the order-button wording «bestilling med forpliktelse til å betale», which is in `order-button-labels.json`). The `nb` withdrawal and confirm labels are therefore authored (UNPROVEN).
