# Pack: resilience

> How the system behaves when its dependencies are down or slow, proven by fault injection in the verify environment.

---

## 1. Policy section

```jsonc
"resilience": {                                // HTTP dependencies = hosts[] entries whose purposes contain "dependency" (03 § 3.3); databases = verifyEnv.databases
  "timeouts": { "upstreamMs": 5000, "pageMs": 8000 },
  "degradable": [ { "dependency": "search.internal", "routes": "web:/blog/**" } ],  // pages that must still render without it
  "formFallback": []                           // RES-008: [{ key: "<UX-022 form key>", db: { db, sql } } | { key, email: "<to>" }] durable record of a submission whose outcome failed
}
```

Faults use the core fault-injection facility (04 § 4.5). Database-down behaviour on pages (non-`api` surfaces) is owned by RTE-007 (web-delivery); this pack covers the rest. Applicability per rule: RES-001 needs a database (`verifyEnv.databases`) or a dependency host; RES-002 and RES-007 a dependency host; RES-003 a `degradable` entry; RES-004 a `hosts[]` entry with `browser: true` that served a script on a browser-sampled page; RES-008 a UX-001 form key with an `email:` or `egress:` outcome. Each is `notApplicable` without its input; RES-005 is `notApplicable` when no fault ran; RES-006 always applies.

## 2. Rules — `RES-*`

- **RES-001** · P0 · http — Dependency unavailable, API surface (pages: RTE-007). Each API-002 example request and each contract-generated request (04 § 15) whose no-fault response was 2xx — at most 50 per service, drawn with the lock-digest PRNG (stream id `res-001`, candidate key = the example id, or `<METHOD> <path template> <status>` for a generated request) — is re-sent in each 04 § 4.5 fault stage other than `delayed` (database stopped; each `dependency` host refused or answering 503). It passes when the response is 5xx with a body valid against `data-api.errorShape`, or when its status and normalised body (03 § 12) equal the no-fault response (the request does not depend on the faulted dependency). A 2xx with different data, any 4xx, or no response within `resilience.timeouts.pageMs` is a finding (`status-mismatch`, showing the request, both statuses and bodies). No `errorShape`: the body check is `notConfigured(errorShape)` and the status check still applies. A service with no contract: the `api`-surface URLs of the `fault-20` sample (GET) are used, with the same pass condition.
- **RES-002** · P1 · http — Slow upstream (the egress proxy holds each request to the dependency for `pageMs` + 5,000 ms before answering): the service responds within `pageMs` with either the page (dependency degraded) or 5xx/503; no request hangs. A request passes with a 2xx or 3xx response having `<main>` text, or a 5xx; a 4xx is a finding `status-mismatch`, and no response within `pageMs` a finding `budget-exceeded`.
- **RES-003** · P1 · http — `degradable` routes, while the listed dependency is refused or answering 503 (04 § 4.5), still answer 200 with `<main>` text whose token overlap with the same route's no-fault response is ≥ `web-delivery.parity.minOverlap` (04 § 12). Probed URLs: for each route group matching the entry's `routes`, its lowest-ranked crawled 200 URL (lock-digest PRNG, stream id `fault-20`), added to the `fault-20` sample for that dependency's fault stages. Owner of those URLs under that dependency's faults: RTE-007 does not judge them. Failure classes `status-mismatch`, `similarity`.
- **RES-004** · P1 · browser — Third-party script hosts blocked: for each `hosts[]` entry with `browser: true` that served a script on a browser-sampled public page, with that host answering connection-refused in the browser (one host at a time, each in its own stage after the fault-injection stages, 04 § 4.2 step 8; browser-side refusal per 04 § 6.1), those pages' rendered `<main>` text overlap with the unblocked render is ≥ `web-delivery.parity.minOverlap` (`similarity`), and the flows run in that stage — every flow whose `requires` list does not contain the blocked host, in file-name byte order — still pass (`flow-step-failed`).
- **RES-005** · P1 · http — Recovery: after each fault ends, within 30 s (one request per sampled route per second), every sampled route again answers the status it answered before the fault, with no service restart.
- **RES-006** · P1 · ast — Each adapter `httpClientApis` call passes the entry's `timeoutArg` (03 § 6; e.g. `fetch` `signal: AbortSignal.timeout(n)`, axios `timeout`, `requests` `timeout=`), or is made on a client created by a `clientFactory: true` entry's call that sets it. Part `bound` (P1): a numeric-literal timeout value, read in the adapter entry's `timeoutUnit` (03 § 6; `ms` or `s`, default `ms`), is > 0 and ≤ `resilience.timeouts.upstreamMs`; a zero, negative or larger literal is a finding (`value-mismatch`, showing the call and value); a non-literal value is not judged by this part. Part `bound-unknown` (W · ast): each call whose timeout value is not a numeric literal (an identifier, call or other expression) is listed, showing the call, since its bound against `upstreamMs` can't be verified. Part `retry`: retry loops around such calls (a loop or recursion whose body catches the call's error) have an integer bound ≤ 10 and a delay call (`clockApis`/`sleepApis`) inside the loop.
- **RES-007** · W · http — 503 responses during dependency failure carry `Retry-After`.
- **RES-008** · P1 · http, browser, db — No false success when delivery fails. For each UX-001 form key (UX-022 definition: `<flow id>#<step index>→<outcome>`, step index per 03 § 10) whose outcome is `egress:<host>` or `email:<to>`, the flow is replayed. Form keys are the G6 UX-001 result of the same run (as UX-022): when G6 did not run or is `BLOCKED`, RES-008 is `blocked(prerequisite: G6)` and never passes on an empty key list. Metadata `gates: [G6]` (the `formFallback` `db` query runs after the faulted flow). Each replay runs in its own mutating stage (04 § 4.2 step 8), once per fault: for `egress:<host>`, the outcome stub (04 § 4.6, server-side and browser-side) answers 500 instead of its declared stub, and, separately, holds its answer for `resilience.timeouts.upstreamMs` + 5,000 ms; for `email:<to>`, the SMTP sink answers `451` to `RCPT TO:<to>` (other recipients are accepted). The flow must contain ≥ 1 UI expectation (`expectText`, `expectUrl`, `expectVisible`) between the submitting step and the outcome step; else a blocking `missing-element` finding owned by `operator` for that key, naming the flow and "no success expectation after the submitting step" (04 § 1.2 required-facts rules; flows are Operator-owned), never `notConfigured`. The faulted run passes when at least one of those UI expectations fails (the page does not claim success), or when the key's `resilience.formFallback` entry shows the submission durably recorded: `db: { db, sql }` — a read-only scalar query whose value after the submission exceeds its value before it; `email: <to>` — a message to that address reached the SMTP sink. All those UI expectations passing while the outcome failed and no fallback recorded it is a finding (`value-mismatch`, showing the key, the fault and the success text shown). `db:` outcome keys: `notApplicable` (database-down: RES-001, RTE-007). A `formFallback` key matching no current form key is a W item. Remote services: `skipped(remote)` (04 § 4.5: no local process, SMTP sink or outcome stub reaches their dependencies), keys listed in the coverage record; `remote: write`.
