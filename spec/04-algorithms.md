# shipgate — 04 Algorithms

> How the Verifier decides things. Every algorithm is deterministic for identical inputs (TR-103) and has conformance fixtures in shipgate's own corpus. Load when implementing the corresponding subsystem.

## 1. Rule outcomes, gate statuses, verdict

### 1.1 Channel → gate (normative)

| Channel | Gate |
|---|---|
| `cfg`, `lock` | G0 |
| `ast`, `graph`, `diff`, `deps`, `cmd` | G1 |
| `data`, `db` (migrations, SQL), `contract` (static validation) | G2 |
| `build` | G3 |
| `http`, `html`, `site`, `contract` (live responses), `db` (runtime checks: JOB-002 job runs, readback and "no side effect" checks after G4 probes) | G4 |
| `content` | G5 |
| `browser`, `db` (checks run after a G6 flow, e.g. PRV-016) | G6 |
| `baseline` (against `--against`, refactor or remote baselines) | G7 |
| Comparisons against `quality/baselines/_main/` (AGT-005, AEO-012, CQ-006, ARC-003, PRF-010, UX-009, IDX-003) | `baseline`-channel comparisons in G5; the others in the gate of the rule's own channel (ARC-003 G1, PRF-010 G3/G6, UX-009 G6, IDX-003 G4; without a valid `_main/` IDX-003 uses the committer time). Only when `_main/` exists with a valid `ci` signature (03 § 12); otherwise that comparison is `skipped(no-main)` with a warning |
| `edge` | G8 |
| `review` | consumed in G9 |
| `hook` | `check` modes only |

A rule spanning several channels is evaluated in each corresponding gate; each finding carries the gate of the channel that produced it.

**`db` and `contract` gates are fixed per detector:** a detector that reads only files (migrations, SQL, contract documents) runs in G2; one that reads the migrated database before the first probe (DB-001, DB-004, DB-009, DB-011 `emulator`, SEC-044 `policies`) runs in G4 right after § 4.2 step 4; one that reads a live response or database state after a G4 probe runs in G4; one that runs after a G6 flow runs in G6. A rule with a `db` or `contract` channel lists the gates its detectors use in metadata `gates` (03 § 5, e.g. `gates: [G2, G6]`); metadata validation rejects a `db` or `contract` rule without `gates`, and a detector that runs in a gate its rule doesn't list.

### 1.2 Per-rule outcome
For each rule × service: `applied` | `notApplicable` (surfaces/packs/kinds exclude it) | `noAdapterSupport` | `skipped(reason)` (mode, profile, remote mode, missing optional input explicitly allowed by the rule's metadata) | `notConfigured(input)` (an input the rule requires is missing) | `blocked(reason)`. Recorded per rule in `report.coverage.rules`.

**Facts-oracle rules (UX-003, UX-013, UX-014, UX-019, UX-020 `social-proof`, `stock` and `timer`, UX-023 part `claims`, UX-024 part `register`, UX-025 part `static`, LOC-001 `address` and `hours`, PRV-029 for markets implied only by builder-written signals):** when the page shows content of the kind the rule checks (claims, testimonials, people, trust marks, logo walls, social-proof widgets, stock counts, countdown timers, commercial terms, unregistered images, tracking or pixel IDs in tags, street addresses, opening hours, signals targeting an undeclared market) and the matching `business.json` key or policy source is absent, the outcome is **not** `notConfigured`. It's a blocking finding with failure class `forbidden-value`, owned by the builder: the content is unsupported and must be removed, or the Operator must supply the facts. Only when no such content exists is a missing key `notApplicable`.

**Required-facts rules (PRV-022 parts `imprint`, `controller`, `kr-ecommerce`, `jp-sct`, `cn-icp`; PRV-025; PRV-029 for markets implied by an Operator-owned signal; PRV-030; PRV-031 part `processors`; PRV-033; PRV-034 part `abn`; PRV-035; UX-001 part `mobile`; UX-025 part `declared`; UX-027 part `declared`; UX-015 when a provider price id is sent and the `prices[]` entry has no `providerId`; UX-022 launch-form confirmations; OPS-005 part `postal` when a bulk email was captured and `business.json` has neither `postalAddress` nor `locations[0].address`; API-003 kind (c) when ids are harvested (no ownership file) and none is found for an operation with path parameters; URL-011 for an alias-host wildcard no concrete host resolves (§ 15 *Alias-host wildcards*); RES-008 when a form key's flow has no UI expectation between its submitting and outcome steps; UX-023 part `minimum`; SEC-018 when no flow fills a password input; SEC-032 without an upload flow; SEC-028 without a logout flow; SEC-040 part `dom`, SEC-041, SEC-048 part `foreign-session` and SEC-063 when payments apply (security § 1 *Payments applicability*) and no flow has `journey: "checkout"`, and SEC-041 when checkout flows exist but none has a `markAmount` step; SEC-067 without a signup flow or without an `openEmailLink` step; SEC-064 part `maxima` when a non-`null` maximum applies and neither `security.session.<kind>Var` nor `<kind>Sec` gives a value; DAT-006 part `fixtures`; DAT-018 part `rights`; LOC-003 for `project.kinds` including `local-business`; TRS-001 contact match (no `business.json` `phones`/`emails`)):** the law, the payment provider, the launch check or the verification itself requires the content or input, so the builder can't fix the finding by removing it. When a page, flow or form the rule applies to needs an Operator fact or Operator-owned input that the Operator's files don't hold (no matching `manufacturers[]` entry, a missing `legal`, `phones`, `postalAddress` or `emails` value, `name` and `legalName` both absent, a missing `prices[].providerId`, a missing `launch-forms.json` entry, a missing `terms.returns.windowDays`, a `hosts[]` entry without `name`, a missing `security.session.idleSec`/`absoluteSec`, no `quality/flows/` flow with `journey: "logout"` and a non-null `account`, a form identity (UX-001) or `checkout`/`signup` journey without a mobile flow, an analytics or advertising `hosts[]` entry without a `ux.trackingIds` entry, a `testimonials[]`/`ratings[]` entry without `incentive`, a missing programmatic fixture file or case, a missing `programmatic.sources.<id>.rights`, no `business.json` or an empty `locations` for LOC-003), the outcome is **not** `notConfigured`. It's a blocking finding with failure class `missing-element`, owned by `operator`, naming the missing key, file or flow. The same holds for the PRV-002/PRV-014 (`consent.banner`), PRV-016 (`accountData` and its keys with a signup flow; part `export` with no stored row), PRV-018 (`ai.assistants`), PRV-021 part `flow` (withdrawal flow and its `expectEmail`), PRV-022 (an undeclared required `legalPages` key; `jp-sct` without `commercialTransactions`), PRV-023/PRV-027 (a checkout flow with no order request and no outcome step), PRV-026 `total` (more than 16 fee entries), PRV-028 (including part `terms`), PRV-033 `in-ecommerce`, PRV-037 and PRV-042 (no identification page, no `dsa.ugcSelectors`, no `report-content` flow, no `legal.dmcaAgent`), PRV-038 `registry` and `representative`, PRV-039 (no withdrawal text page), PRV-040 `register` and PRV-041 (`business.json` values, `subscribe` flow) outcomes that their pack text says are owned by `operator`. When it's the only kind of blocking finding left, the run ends in an `operator-owned` handoff (§ 1.9), never a PASS.

### 1.3 Finding status
`blocking` (stable, P0–P2, not debt, not waived, not overridden) | `debt` | `waived` | `experimental` (lifecycle experimental, or override `warn`) | `warning` (severity W) | `exhausted` (repair budget used up; still blocking for the verdict, but allows a handoff).

### 1.4 Gate status
The statuses are tested in the order listed; the first that holds is the gate's status. A gate's `blocking` and `exhausted` findings are reported, and count in § 1.6 step 3 and § 1.9, whatever its status.
- `BLOCKED` — the gate could not run (tool error, toolchain missing, port/engine failure, licence, budget exhausted), a prerequisite gate is `BLOCKED`, a check in it is `blocked(prerequisite: …)` (§ 1.5), or a `†` rule in it is `blocked(reason)` (non-† `blocked` rules become warnings). Its owner is set by § 15 "Owners of BLOCKED gates".
- `NOT_CONFIGURED` — a `†` rule in the gate is `notConfigured` (non-† `notConfigured` rules become warnings). Its owner is set by § 15 "Owners of BLOCKED gates".
- `SKIPPED` — no applicable rules for this run (e.g. G7 without `--against`, G5 when no programmatic family exists and every rule with a `content` channel outside the programmatic pack (CQ-002, CQ-008, CQ-010) is `notApplicable`, G3 for remote-only services, G8 without `previewUrl` and without `edge.production`).
- `FAIL` — at least one `blocking` or `exhausted` finding.
- `PASS` — otherwise.

`noAdapterSupport` never changes a gate status or the service's coverage level; the level is the adapter's earned tier (02 § 1, § 1.6 "Coverage levels", CFG-007). The outcome is counted in `report.coverage.rules`.

### 1.5 Prerequisites and stopping
| Gate | Needs (not BLOCKED) |
|---|---|
| G0 | — |
| G1, G2 | G0 |
| G3 | G0 |
| G4 | G3 (local services) |
| G5 | G4 crawl completed |
| G6 | G4 environment up |
| G7 | G4 + a valid baseline |
| G8 | G0; the UX-022 and SEC-065 checks also need G6 (they read its UX-001 form inventory and `journey: "checkout"` flows) |
| G9 | all others finished |

**Subset runs** (`--gate`, `--pack`, `--service`) first run, for the selected services, the infrastructure their selected gates need, without evaluating those gates' rules and without reporting their gate status: for G4, the G3 builds; for G5, G6 and G7, the G3 builds, § 4.2 steps 1–7 and the G4 crawl. Build, start and migration failures there are reported as BLD-004, BLD-005 and DB-001 `apply` findings, with the per-service consequences of the exception paragraph below; nothing else from the unselected gates is reported. Gates neither selected nor needed are `SKIPPED(scope)`.

A check that needs G6 while G6 is `BLOCKED` is `blocked(prerequisite: G6)` with the owner of G6's block; while G6 is `SKIPPED(scope)` it is `skipped(scope)` (the run is partial anyway). Such a check never passes on a form or flow list that G6 did not produce in the same run.

A gate whose prerequisite is `FAIL` still runs; only `BLOCKED` stops dependents. The whole run stops early only on: CFG-001, CFG-008, licence, invalid lock signature. Build or start failures are findings (BLD-004/005), not run-stoppers. Exception, per service: when service s has a BLD-004 finding, every G4–G7 check of s is `blocked(prerequisite: BLD-004)`; when s has a BLD-005 finding, its remaining G4 checks and its G5–G7 checks are `blocked(prerequisite: BLD-005)`; when a database of s has a DB-001 `apply` finding (migrations don't apply), s's later G4–G7 checks are `blocked(prerequisite: DB-001)`. Other services' checks run. A gate with any such check is `BLOCKED(prerequisite)`, owner `builder` (BLD-004, BLD-005 and DB-001 `apply` are all fixed in the Builder's code).

**After an early stop**, every gate not finished is `BLOCKED(stopped: <cause>)` with owner `operator` (CFG-001, CFG-008, the licence and the lock signature are Operator inputs). Before stopping, shipgate still runs the diff parts of AGT-001 and AGT-006 (they need no toolchain); their findings count as findings of a gate that ran for *Builder work first* (§ 1.9). The base verdict is `BLOCKED` (§ 1.6 step 2) and the handoff reason is `operator-owned`, subject to that condition.

### 1.6 Verdict
The verdict is computed in two steps, so a narrow run can never hide a failure.

**Step 1: base verdict** over the gates that ran. Gates excluded by the run's scope (subset flags, `--changed` scoping, reduced mode) are `SKIPPED(scope)` and count neither as BLOCKED nor as PASS.
1. If at least one gate is `BLOCKED` or `NOT_CONFIGURED`, every such gate has owner `builder`, no service is below `minCoverage` and the lock is valid (§ 15 *Owners of BLOCKED gates*: e.g. it traces back through prerequisites to a BLD-004/BLD-005/DB-001 `apply` failure, it is builder-owned `BLOCKED(budget)` (§ 8), or a `NOT_CONFIGURED` gate whose missing input lies inside the Builder's `writeScope`) → `FAIL`. Breaking the build or startup, or making the app slower, never yields `BLOCKED` or a handoff.
2. Otherwise → `BLOCKED` if any gate that ran is `BLOCKED`/`NOT_CONFIGURED`, any service is below `minCoverage`, or the lock is invalid.
3. Otherwise → `FAIL` if any finding is `blocking` or `exhausted`.
4. Otherwise → `PASS`.

**Implied baseline:** when a signed `quality/refactor.json` exists, `verify` runs as `verify --against <refactor.json baseline>` (G7 included). A site rebuild is just a refactor whose baseline is remote: `init --new` replacing a site, or `baseline --from-remote`, writes a signed `refactor.json` with `baseline` set to the remote baseline id and `goal: "replatform"` (05 § 2.1). An agent therefore can't finish a refactor or re-platforming without the behaviour checks. Removing `refactor.json` is an Operator action (it's a protected, signed file).

**Step 2: scope downgrade.** A run is *partial* when it is any of:
- `check`;
- `verify --changed`;
- a subset run (`--gate`, `--pack`, `--service`);
- `verify --adopt`;
- a reduced run;
- a run with any timing rule `skipped(slow-host)` (TR-111);
- a run where planned services are skipped (CFG-009, `project.stage: "new"`);
- a run with any P0 or P1 rule `skipped(incomplete-crawl)` (§ 10);
- a run with any check `skipped(host-unsupported)` whose G8 is `SKIPPED` (§ 3);
- a run with `--resume` (§ 15 `verify --resume`: it reuses finished gates of the previous run, also under `--no-cache`).

For a partial run, a base `PASS` becomes `PARTIAL`; a base `FAIL` or `BLOCKED` is reported unchanged. A `PARTIAL` verdict never produces a sealed PASS.

**Reduced runs** (G0–G3 only) happen only when the signed policy allows them (`verifyEnv.reduced`, 03 § 3.4) **and** the environment really lacks a browser or free ports. shipgate probes this at run start: *no browser* = the pinned Chromium doesn't launch and load `about:blank` within 30 s; *no free ports* = it can't bind, on `127.0.0.1` after 3 attempts 1 s apart, one TCP port per service, embedded database, front-proxy origin host and platform process, plus one each for the SMTP sink, egress proxy, forward proxy and canary. Environment variables, user config and command-line flags can't switch reduced mode on, so an agent can't grant itself a stop.

**Coverage levels:** `full` (Tier 1) > `structural` (Tier 2) > `behaviour` (Tier 3), by earned tier.

### 1.7 Review results
`quality/audit/review.json` entries affect only rules with a `review` channel. Rules whose only channel is `review` are W. For rules with automated channels plus `review`, an Auditor `fail` produces a finding at the rule's severity. Without `review.json`, or without an entry (`rule`, `target`) for a target the rule covers, a review-only rule is `skipped(no-review)` (a warning) and an automated-plus-review rule is judged by its automated channels only. G9 is `PASS` unless a review `fail` produced a blocking finding (then `FAIL`).

### 1.8 Partial severities
A rule may declare `parts: [{ part, severity }]` in its metadata (03 § 5). Every finding carries a `part` (default `main`, which has the rule's own severity); the detector that emits the finding sets it. The part is independent of the failure class, so two parts may emit the same class. Waivability follows the rule unless the part's metadata sets its own `waivable` (`parts: [{ part, severity, waivable?, remote? }]`); W parts are always waivable. A part's severity is static: a severity that depends on an input ("P0 with X, otherwise W", "unknown → W") is two parts, each with its own static severity; when the missing input makes the part undecidable rather than weaker, the outcome is `notConfigured(<input>)` instead (e.g. SEC-029 `expiry`, SEC-037 `expired` and SEC-044 `signed-url-expiry` without `auth.tokenTtlVar`). Rules described in packs as "the X part is W" are encoded this way, for example:
- **RTE-010:** `behaviour` P0†, `empty-ua` W, `source-hint` W.
- **AGT-004:** `transform` P0†, `derived-expectation` W.
- **AGT-010:** `swallow` P0†, `fallback-unlogged` W.
- **SEC-050:** `provider-pattern` P0†, `env-value` P0†, `env-file` P0†, `entropy` W, `history` P0. The `history` part is not †: it is Operator-owned debt with no expiry, recorded at adoption, and it clears only when `debt rotate` sets `rotatedOn` (05 § 1). Until then every report lists it.
- **Input-dependent security parts:** SEC-025 `rate-limit` P1 / `rate-limit-edge` W; SEC-054 `requests` P1 / `requests-edge` W; SEC-052 `licence-unknown` W and `deprecated-unknown` W; SEC-053 `age-unknown` W; SEC-073 `version-unknown` W.

### 1.9 Handoffs
The Verifier writes a handoff (03 § 15, inside the sealed record) **only** in these cases; in every other case there is none, and the agent must keep fixing:

| Reason | Condition |
|---|---|
| `exhausted` / `operator-owned` | Base verdict `FAIL` reached at § 1.6 step 3, with at least one blocking finding, every blocking finding being `exhausted` or owned by `operator` |
| `operator-owned` / `budget` | Base verdict `BLOCKED`, and every BLOCKED/NOT_CONFIGURED gate has owner `operator` (missing input, no baseline, licence, budget, coverage); a service below `minCoverage` counts as an `operator` cause |
| `tool-error` | Base verdict `BLOCKED` caused by a shipgate tool error (exit 3) |
| `reduced-environment` | Reduced run, or run with `skipped(slow-host)` timing rules, only when the signed policy allows reduced runs (`verifyEnv.reduced.allowed: true` and its `where` satisfied, 03 § 3.4; without it a slow host gives `PARTIAL` and no handoff), whose base verdict is `PASS` and whose only partial causes (§ 1.6 step 2) are these two: not `check`, `--changed`, `--gate`, `--pack`, `--service` or `--adopt`, no planned services skipped, nothing `skipped(incomplete-crawl)` or `skipped(host-unsupported)` |
| `planned` | New-project run (CFG-009) whose base verdict is `PASS` and whose only partial causes (§ 1.6 step 2) are skipped planned services and, only when the signed policy allows reduced runs (as in the row above), a reduced run or `skipped(slow-host)` timing rules; lets an agent stop between milestones of a project that isn't fully built yet |
| `break-glass` | A valid Operator-signed break-glass for the tree hash (04 § 8.1) |
| `unverified-stop` | Loop guard (04 § 8.1) |

**Builder work first.** No handoff is written (except `break-glass` and `unverified-stop`) when (a) a finding in a gate that ran is `blocking` with owner `builder` (`exhausted` findings don't count), or (b) a gate is `BLOCKED(budget)` with owner `builder` (§ 8). The stop message lists those findings and gates.

**`reason` value** (`handoff.json`, 03 § 15) for rows with two reasons: `exhausted` when at least one blocking finding is `exhausted`, else `operator-owned`; `budget` when any `BLOCKED` gate's reason is `budget`, else `operator-owned`. When several rows match, the first of `tool-error`, `budget`, `exhausted`, `operator-owned` wins.

## 2. Verify environment identity

1. Each local service starts with `SITE_URL` (or the adapter's equivalent) = its origin, `DEPLOY_ENV=production`, `SHIPGATE_VERIFY=1`, `PORT={port}`.
2. **One front proxy per origin host.** Services on the same host are mounted by path prefix (`services[].mount`, longest prefix wins; default `/`). The proxy terminates TLS with a per-run certificate for the host, issued by a per-run CA; forwards with `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto: https`, `X-Forwarded-For: 203.0.113.10` (a TEST-NET address, so apps that trust loopback forwarding aren't fooled and SEC-021's `127.0.0.1` bypass probe stays meaningful). The exception is probe requests that shipgate itself marks with an internal header, which the proxy strips; for those it passes the probe's own `Host`, `X-Forwarded-Host`, the SEC-021 `override-headers` (including `X-Forwarded-For`/`X-Real-IP`) and the I18-011 country headers (ruleset `geo-headers.json` `headers`) through unchanged (SEC-038 host-header poisoning, SEC-021 header-based bypass, I18-011 geo serving); applies host emulation (§ 3) and, for Supabase-style platforms, the gateway routes (§ 4.4).
3. HTTP probes go to the proxies directly. **Browsers** reach origins through Playwright's `proxy` option pointing at shipgate's forward proxy, which routes origin hosts to their front proxies and everything else per the third-party policy (§ 6.1). TLS trust: Chromium with `--ignore-certificate-errors-spki-list=<CA SPKI>`; Firefox with a per-run profile importing the CA; WebKit with `ignoreHTTPSErrors`.
4. **Preview pass:** a second **build and start** of each local service with `DEPLOY_ENV=preview` and `SHIPGATE_VERIFY` unset (adapters declare `envInlinedAtBuild`; when false, a restart without rebuild is enough). Probes the 20-URL sample per surface `preview-20` (§ 10 "Fixed-size samples") for IDX-005, RTE-004 `status` (each sampled URL must answer the Status column of its RTE-004 row) and SEC-033. It runs as an extra stage on a database freshly restored from the template (§ 4.2 step 8), after the read-only G4 stage and before the first mutating stage; the next stage restarts the services in the main-pass environment. `static-html` services: host emulation only. Remote services: `SKIPPED`.
5. **Edge pass (G8):** read-only GET/HEAD checks of rules that list the `edge` channel, plus, for paths whose host directive is unsupported (§ 3), the `http` checks of rules that were `skipped(host-unsupported)`, even without an `edge` channel; against `previewUrl` (with `edge.bypassHeaderVar` for deployment protection), and, when `edge.production: true`, read-only checks against `production.origins`:
   - HEAD for host identity (apex↔www, http→https, HSTS, TLS, caching headers) and for each `aliasHosts` entry (URL-011); GET for the social preview fetcher user agents on the homepage (MET-005 `fetchers-edge` part, which compares `og:*` values from the body); with `edge.production: true`, GET for the URL-014 path variants of `/` on each `production.origins` entry (at most 8 requests per origin, redirects not followed);
   - when `project.stage: "live"`, a **bounded GET launch check**: `robots.txt`, the sitemap index plus at most 10 child sitemaps, the homepage and 20 sitemap `<loc>` URLs sampled with the lock-digest PRNG (IDX-011). That is at most 33 requests per origin at 1 request per second, without cookies, using shipgate's own user agent; robots.txt is evaluated for the Googlebot and Bingbot groups.

   Against `previewUrl`, the IDX-005 `preview-edge` part makes one unauthenticated request (no bypass header) to the homepage and `robots.txt`.

   Also in the edge pass:
   - SEC-058 `edge`: two anonymous GETs per cache-deception variant URL (at most 3 variants × 5 route groups);
   - SEC-059: DNS lookups and two GETs (https and http root) per listed host;
   - SEC-079: one anonymous GET per `probePaths` entry of ruleset `object-storage-hosts.json` for each object-storage candidate host covered by a `hosts[]` entry, at most 20 hosts per run (lock-digest PRNG, stream id `SEC-079`);
   - REF-010 (and `old-origin`): 20 recorded remote-baseline URLs drawn with the lock-digest PRNG (§ 15, stream id `REF-010`) plus every recorded `url-move` source, mapped onto the checked origin, at most 200 URLs per origin;
   - SEC-034 exposed-path probes: the ruleset path list only, no backup-copy variants against production;
   - SE-008 and AEO-008 user-agent checks: homepage + the first 5 URLs of the edge sample per listed agent;
   - MET-014 parts `indexable` and `resolve`: the media set of the homepage and the first 5 URLs of the edge sample, at most 50 requests per origin;
   - URL-015: each http→https, apex↔www and URL-011 alias-host homepage probe repeated once with the campaign query (at most 2 + the number of alias hosts requests per origin);
   - CRW-001 TTFB: the family and hub pages among the edge sample (none → `notApplicable` in the edge pass);

   The **edge sample** is the IDX-011 sample against `production.origins` and the `preview-20` sample (paths mapped onto `previewUrl`) against `previewUrl`; "first" means lowest position (§ 10 "Fixed-size samples"; for the IDX-011 sample, PRNG rank). When `project.stage` isn't `live`, the production edge sample is the `preview-20` sample's paths mapped onto each `production.origins` entry.
   - AEO-002 `sameAs` HEAD, OPS-006 DNS lookups and SEC-015 `security.txt`: one request each; OPS-016 (with `edge.production`): one GET of the IANA RDAP bootstrap file per run plus one RDAP GET per registrable domain of `production.origins`;
   - SEC-065: each recorded checkout route plus its same-origin scripts, at most 30 requests per origin;
   - CFG-009 safety net (stage `new`): `/` and the sitemap index, 2 requests.

   **Limits for every edge request:** 1 request per second per origin, GET/HEAD only, no cookies, and shipgate's user agent unless a rule tests a specific one.

   Without either: `SKIPPED` with the list of edge rules.
6. **Comparison pass (AGT-011):** after G6, each local service restarts with exactly the main-pass environment except that `SHIPGATE_VERIFY` is unset, with no rebuild unless `envInlinedAtBuild`. PRV-001 (browser), SEC-010, RTE-013 and MET-011 (all parts except `dead-anchor`) re-run on the 10-URL sample per surface `comparison-10` (§ 10 "Fixed-size samples"). It runs as an extra stage on a database freshly restored from the template (§ 4.2 step 8), after the last G6 mutating-flow stage (including REF-013 `sw-cache`) and before the control click probe. For each (rule, part, URL) of the `comparison-10` sample that was checked in the main pass without a finding, a finding in this pass is an AGT-011 finding (evidence: URL, expected = the main-pass observation, actual = this pass). Triples not checked in the main pass are ignored. Remote services: `SKIPPED`.
7. **Fixture pass (programmatic § 7):** when the programmatic pack is enabled and a family in `inventory` mode has a fixture file, shipgate writes the fixture inventory to `quality/out/fixtures/inventory/`, then builds and starts each service serving that family a second time with `SHIPGATE_INVENTORY_DIR` set to that directory and otherwise the main-pass environment. It runs as an extra stage on a database freshly restored from the template (§ 4.2 step 8), after the read-only G4 stage and the preview pass and before the first G4 write probe; the next stage restarts the services in the main-pass environment. Every fixture row is checked (no sampling) by the rules programmatic § 7 lists. Live-mode families: `skipped(live-mode)` (programmatic § 7). Remote services: `SKIPPED`.

## 3. Host emulation

| Host | Files | Supported |
|---|---|---|
| vercel | `vercel.json` | `redirects`, `rewrites`, `headers`, `cleanUrls`, `trailingSlash` |
| netlify | `netlify.toml`, `_redirects`, `_headers` | redirects/rewrites with status, splats, placeholders; headers; force |
| cloudflare-pages | `_redirects`, `_headers` | Netlify file syntax subset (below) |
| nginx | `quality/host/nginx.conf` | `return`, `rewrite … permanent\|redirect`, `add_header`, `location` prefix/exact/regex, `try_files` |
| apache | `.htaccess` | `Redirect`, `RedirectMatch`, `RewriteRule` `[R=301\|302,L]`, `Header set` |
| none | — | pass-through |

**Syntax** (what the Supported column means; "unsupported" = shipgate doesn't emulate it):
- vercel: `source` in path-to-regexp syntax (`:name`, `:name*`, `:name+`, `(regex)`); `destination` with `:name` substitution; `permanent` (`true` → 308, `false` → 307) or `statusCode`; `headers` entries `{ source, headers: [{ key, value }] }`. Entries with `has`, `missing`, `locale` or `basePath`, and `rewrites` whose `destination` is an absolute URL, are unsupported.
- netlify and cloudflare-pages `_redirects`: one rule per line, `source destination [status]` (default 301; 200 = rewrite), `*` splat substituted as `:splat`, `:name` placeholders; a trailing `!` on the status (force) only on netlify. Query-string matching, country/language conditions and, on cloudflare-pages, `!` are unsupported. netlify.toml `[[redirects]]` with `from`, `to`, `status`, `force`; its `conditions`, `query` and `signed` keys are unsupported; `[[headers]]` with `for` and `[headers.values]`. `_headers`: a path line, then indented `Name: value` lines; a `! Name` line is unsupported.
- nginx unsupported: `if`, `map`, `set`, `proxy_pass`, `fastcgi_pass`, `error_page`, `auth_basic`, `limit_req`, `sub_filter`, and `add_header` inside `if`.
- apache unsupported: `RewriteCond`, `RewriteMap`, `ErrorDocument`, `SetEnvIf`, `Require`, and `Header` other than `set`, `always set`, `unset`.

A directive is *unsupported* only when it is named unsupported above, or it is a redirect, rewrite or header directive of the host that the Supported column doesn't list. Every other directive, i.e. one that neither redirects, rewrites nor sets headers (e.g. `listen`, `server_name`, `root`, `Options`, `DirectoryIndex`, `gzip`, `ssl_*`), is ignored without a finding.

**Order.** vercel: `headers` (all matching entries apply, later wins per header name), then `redirects` (first match wins), then `cleanUrls`/`trailingSlash`, then `rewrites` (first match). netlify and cloudflare-pages: redirect/rewrite rules in file order (`_redirects` before `netlify.toml`), first match wins; a rule without `force` applies only when no file exists at the path; all matching `_headers` entries apply. nginx: location selection by nginx rules (exact `=`, then longest `^~` prefix, then the first matching regex in file order, else the longest prefix); `return` and `rewrite … permanent|redirect` stop processing. apache: `.htaccess` directives in file order; `[L]` ends the rewrite chain.

Each unsupported directive is a W finding (`host-directive-unsupported`, file:line). For every URL matched by its source pattern (every URL of the service when the pattern can't be evaluated), the G4 `http` checks of status, redirects and response headers (URL-\*, IDX-\*, RTE-004, and security-pack rules with failure class `missing-header` or `header-value`) are `skipped(host-unsupported)` and run in G8 against the same paths instead (§ 2 step 5): on at most 20 of the matched URLs per source pattern, drawn with the lock-digest PRNG (stream id `host-unsupported`), under the § 2 step 5 request limits. The report lists the matched URLs not checked. When G8 is `SKIPPED`, any `skipped(host-unsupported)` makes the run partial (§ 1.6 step 2).

## 4. Processes, databases, platforms, fault injection

### 4.1 Process supervisor
Windows Job Objects / Unix process groups; `shell` per command (`none` = direct exec, default); environment = user environment + policy `env` + shipgate variables; logs to `quality/out/logs/<service>.log`; readiness (03 § 3.4 `health`): poll `verifyEnv.health.<service>.url`, starting at `intervalMs` and doubling after each failed attempt up to 5,000 ms, until a 200–399 response (redirects not followed; with `endpoint: true` only 200) or `timeoutSec`; whole tree killed on exit; Windows long paths and `.cmd` shims handled.
- **Graceful stop (OPS-012):** on Unix, SIGTERM, then wait up to `ops.shutdownSec`, then kill. On Windows, the tree is killed directly, so OPS-012 is `skipped(platform)`.
- **Missing-variable start probe (OPS-010):** in G4, after BLD-005 passed for the service, each service is started once more with one required env-module variable removed (chosen by the lock-digest PRNG, stream id `OPS-010`). Expected outcome: a non-zero exit within `verifyEnv.health.<service>.timeoutSec`, with the variable's name in the output. It runs as its own stage on a database freshly restored from the template (§ 4.2 step 8), after the read-only stage and before the preview pass; the next stage restarts the service in the main-pass environment.

### 4.2 Database lifecycle
1. Start each `embedded` database (PostgreSQL, MySQL, SQLite file) from the managed toolchain on a free port, temp data dir, current user. When shipgate runs as root (Unix, e.g. in a container), the database process drops to the unprivileged user `nobody`; when that drop fails, the gate is `BLOCKED(root-container)`, owner `operator`, and the report says the database must be `external`.
1a. An `external` database (`databases[].provider: "external"`, 03 § 3.4; CFG-004 applies) is not started, snapshotted or restored. Migrations (step 4) and seeds (step 5) run against it only when the policy sets `databases[].migrateExternal: true`; otherwise both are skipped and listed. Every mutating stage (step 8) and fault stage (§ 4.5) of a service that uses it is `skipped(external-database)` and listed in the report; the read-only stage runs. DB-* checks that need a snapshot or a fresh instance are `skipped(external-database)`. This mirrors § 4.4 *Fallback (`external`)*.
2. Missing in the pinned build → `BLOCKED` listing them (owner per § 15 "Owners of BLOCKED gates").
3. Platform prep (addon adapters) before migrations (§ 4.4).
4. Migrate: `data-api.db.migrations` (format + dir; overrides the adapter default) applied natively for `sql-dir`, otherwise the `migrate` command of the service named by `data-api.db.service`. Statement logging is on during this step (PostgreSQL `log_statement = all`, the MySQL general log); for non-`sql-dir` formats whose adapter declares `migrations.applyCommand`, each pending migration file is applied by its own invocation, so the logged statements are attributed to that file (DB-003, DB-006). For MySQL, before a pending migration file that changes a column type on a `largeTables` table is applied, the DB-003 `rewrite` probe runs: `CREATE TABLE sg_probe LIKE <table>`, the same `ALTER TABLE` on `sg_probe` with `, ALGORITHM=INSTANT` appended, else with `, ALGORITHM=INPLACE, LOCK=NONE` appended, then `DROP TABLE sg_probe`.

8. **Mutating stages run one after another** in a fixed order. Every rule or part whose text says "(mutating stage, 04 § 4.2 step 8)" runs in one, and anything that writes, logs out or locks out an account must be marked that way. Probes in the read-only stage never change state.

   The order: G4 write probes; each rule or listed part below is its own stage, in the listed order (the bullets only group them). Items joined by `/`, by "and", or listed in one parenthesis are one stage; items separated by commas are separate stages in the order written:

Where no Supabase Auth build exists for the OS, `/auth/v1/*` isn't emulated: the service needs `external` (CFG-004) to log in; without it, rules that need a logged-in session on that service are `notConfigured(supabase-auth)` (owner `operator`, § 15), and the report names the OS.

### 4.5 Fault injection (core G4 facility)
Used by RTE-007 (owner of dependency-failure behaviour), RES-*, OPS-002 and OPS-003 `event`. Dependencies come from the `hosts` registry (entries whose `purposes` contain `dependency`, 03 § 3.3) and databases (`verifyEnv.databases`). Faults: database stopped; HTTP dependency refused (the egress proxy resets the TCP connection without a response), delayed (the egress proxy holds the response for `resilience.timeouts.pageMs` + 5,000 ms, RES-002: longer than the page budget, so a service with no upstream timeout can't answer within `pageMs`), or answering 503 (egress proxy). Each dependency is faulted alone: one stage per dependency × fault, each on a fresh database instance (§ 4.2 step 8), against the 20-route sample per surface `fault-20` (§ 10 "Fixed-size samples"), plus, in the stages of a dependency named in `resilience.degradable`, the RES-003 probe URLs (for each route group matching the entry's `routes`, its lowest-ranked crawled 200 URL, stream id `fault-20`). In the database-down stage, OPS-002 also requests each `endpoint: true` health URL and OPS-003 `event` also sends the API-002 example and generated requests (§ 15 *Contract request generation*).

Remote services have no local process, database or egress path: their fault stages (this section) and delivery-fault stages (RES-008, § 4.6) are `skipped(remote)` whatever the rule's `remote` metadata, and RTE-007, RES-001…RES-003, RES-005, RES-007 and RES-008 list the skipped URLs or form keys in the coverage record.

### 4.6 SMTP sink and egress proxy
Local SMTP on `{smtp.port}` captures all mail for flows and OPS checks. Server egress: services get `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` and `NODE_USE_ENV_PROXY=1`. `NO_PROXY` lists only the exact `host:port` pairs of the verify environment's own databases, platform processes, SMTP sink and sibling services, never whole loopback or private ranges, so requests to other internal addresses stay observable. For SSRF probes (SEC-046), shipgate also runs canary listeners on `127.0.0.1` and `[::1]` and on the loopback alias `10.255.255.1` (one free port, chosen once per run and used on all three addresses). When shipgate can't bind the alias (e.g. Windows without admin rights), only the egress-proxy and loopback canaries are used and the report says so. A probe counts as successful SSRF if a canary or the egress proxy receives a request carrying the probe's nonce, or if the response contains canary content.
- The proxy itself serves `ssrf-redirect.shipgate.test`, which answers with a 302 to the loopback canary (the redirect-to-internal probe).
- `*.shipgate.test` names never resolve outside the verify environment.
- The proxy records every connection to a loopback, private or link-local address.
- Requests to model-provider hosts (`hosts[]` entries with purpose `ai`, plus the ruleset `model-hosts.json` list) are stubbed in every stage, server-side and in the browser (§ 6.1), answered with their `ux.egressStubs` entry or else `200 {}` (`application/json`), so probes and flows never spend real tokens and stay deterministic.
- **Outcome stubs win over forwarding:** a host named in any flow's `expectEgress` or in `ux.egressStubs` is always answered by its stub, server-side here and browser-side in § 6.1, for the whole run, even if `hosts[]` marks it `server: true` or `browser: true`. Form submissions, CRM leads and emails to real third parties never leave the verify environment. Requests answered by a stub are recorded but are not SEC-004 `egress` findings.
- **Delivery faults (RES-008):** in a RES-008 stage (§ 4.2 step 8) the outcome stub of the faulted `egress:<host>` form key answers `500` with an empty body, or, in the second stage for that key, holds its stub answer for `resilience.timeouts.upstreamMs` + 5,000 ms, server-side here and browser-side (§ 6.1); for an `email:<to>` key the SMTP sink answers `451 4.3.0` to `RCPT TO:<to>` and accepts every other recipient.
- **Forwarding:** the egress proxy forwards only to `hosts` entries with `server: true` that no stub answers. Every other destination is recorded (SEC-004 `egress` finding) and answered `502` with header `X-Shipgate-Egress: blocked`, never forwarded. The proxy also serves fault injection (§ 4.5). Processes ignoring proxy variables can't be contained without OS sandboxing; the report says so.
- **G1 tests:** when TST-004 applies, the egress proxy starts before G1 and G1 test commands get the same proxy variables, so TST-004 `egress` reads its records; in reduced runs TST-004 `egress` is `skipped(reduced)`.

## 5. Diff base and sensitive paths

- **Hook sessions:** at the first `check` of an agent session, shipgate snapshots tracked files, untracked non-ignored files, and a fixed list of **ignored but sensitive paths** (`quality/verify.env`, git-ignored `.env*` files (never the tracked `.env.example`, `.env.sample`, `.env.template` or `.env.dist`, which OPS-010 requires the Builder to keep current), and the git-ignored files matching the agent-host config patterns of 05 § 3: `.claude/**` (incl. `.claude/settings.local.json`), `.codex/**`, `.cursor/**`, `.opencode/**`, `.agents/**`, `.gemini/**`, `.windsurf/**`) into the state dir. A changed hash on a sensitive path is a P0 AGT-001 finding; a changed `verify.env` additionally requires the Operator to re-lock (the lock stores `verifyEnvSha256`).
- **Base.** `check` modes compare against the session snapshot. Every `verify` (in a hook session or not, local or CI) compares against the merge-base of `HEAD` and `baseBranch` (03 § 3.1; the local branch, else `origin/<baseBranch>`), plus uncommitted and untracked non-ignored changes. The sensitive paths, which git doesn't track, are compared against the session snapshot when the `verify` runs in a hook session that has one, and are not compared otherwise. When neither `baseBranch` ref resolves (shallow clone, branch not fetched, unborn branch) or no merge-base exists, diff rules behave as with no git: `†` diff rules are `blocked(no-base)` with owner `operator` (the report asks for the branch or a deeper fetch), non-† diff rules are `skipped(no-base)`.
- **Verifier outputs** (`quality/out/**`) are not part of the snapshot: they change on every run. Instead shipgate records the SHA-256 of every file it writes there (reports, `handoff.json`, `break-glass.sig` it accepted) in the state dir; any content in `quality/out/` that doesn't match a recorded digest is ignored by every shipgate reader and reported as W (`foreign-output`).
- **No git:** `†` diff rules are `blocked(no-git)` (the run is `BLOCKED`); non-† diff rules `skipped(no-git)`. Remote-only projects have no diff rules applicable.
- Known limit: a session snapshot taken after another session's uncommitted edits treats them as base for `check` modes; every `verify` (merge-base diff) catches this.

## 6. Browser

### 6.1 Driver matrix
| Need | Driver |
|---|---|
| Flows, axe-core, computed styles, hidden-text checks, raw-vs-rendered parity, layout, screenshots | Playwright (managed Node) with its pinned Chromium; Firefox/WebKit when listed |
| Page-load performance | Lighthouse navigation mode (managed Node) on the same Chromium |

**Verifier HTTP client** (every `http`, `html`, `site`, `contract` and `edge` request and the crawl, unless a rule states otherwise): user agent `Mozilla/5.0 (compatible; shipgate/<verifierVersion>)` ("shipgate's own user agent"); `Accept: text/html,application/xhtml+xml,*/*;q=0.8`; `Accept-Language: en` unless the rule names a locale; `Accept-Encoding: gzip, br`. HTTP/1.1, and HTTP/2 when negotiated by ALPN. No cookies unless a probe states them (a session, a probe cookie); redirects not followed unless the rule says so. Connect timeout 10 s, total timeout 30 s per request; after a network error or timeout one retry 1 s later (the crawl's "after one retry", § 10), and a second failure is the request's outcome. A response body is read up to 20 MiB; a longer body is cut at 20 MiB and the response marked `truncated` in the evidence. Local origins are reached through the front proxy (§ 2 step 2), trusting the per-run CA; remote TLS is verified normally against the toolchain's root store.

**Third-party requests in the browser:** every request to a host other than the project's origins is intercepted (Playwright `route`): recorded (for PRV-*, PRF third-party budgets), then fulfilled by the real host only if it is in `hosts` with `browser: true` and is neither an outcome-stub host nor a model-provider host (§ 4.6, both answered with their stub); otherwise answered with `204` (scripts: empty body, `application/javascript`). In a RES-004 browser host block stage (§ 4.2 step 8) the blocked host is aborted with `connectionrefused` (Playwright `route.abort`). Errors thrown by scripts from non-origin hosts are excluded from RTE-013/TST-009. Lighthouse runs with the same policy; third-party costs are reported separately (PRF-006).

### 6.2 Aggregation
Lighthouse runs `performance.lighthouse.runs` times per sampled URL; median per URL; maximum across URLs of a route group, compared per metric with the budget of the most specific `performance.routes` key matching the route group's pattern (most literal path segments; ties → longest literal prefix, then lexicographic). Metrics that key doesn't set come from `performance.defaults`.

### 6.3 Host calibration (TR-111)
At the start of the first of G4 and G6 that runs, before any timing measurement, shipgate runs Lighthouse's benchmark 3 times and records the median `benchmarkIndex` in the report. Timing rules compare against it (TR-111).

## 7. `brief`

Deterministic; free text is never interpreted.
**Inputs:** `--paths`, `--routes`, `--service`, `--surface`, `--family`, `--kind feature|fix|refactor|migration|content|dependency`, `--tags`.
**Resolution:** path → service → file role (§ 7.1) → routes/surfaces → enabled packs → rules whose `appliesTo` matches (+ kind rules: refactor → REF-*, migration → DB-*, dependency → SEC-051/052, ARC-007, AGT-009). Several `--paths` are a union. `--routes` and `--family` select services and surfaces like a path and add the rules whose `appliesTo.surfaces` include them (union with the path result); `--service` and `--surface` restrict (intersect) the result; `--tags` keeps only rules with a matching tag; `--kind` adds its kind rules (union).
**Output:** ≤ 40 rules ranked severity → gate → id, each with title and fix hint; policy excerpts = the policy blocks of the packs that own the listed rules, keys sorted, cut at 60 lines; for files of role `route`, `layout` or `component` (§ 7.1) and files matching `**/*.{md,mdx,markdoc}` outside `quality/` and the repository root, `business.json` excerpts (every key present in the file, 03 § 14; keys sorted; ≤ 40 lines, arrays cut in file order with the count of omitted entries) with the instruction of TR-112.
**Delivery:** session start (repo summary = project kinds, stage, services with adapter and coverage level, enabled packs, last verdict; ≤ 40 lines), first touch of each file (`brief --paths`), prompt submit (rules with a `tag` equal to a prompt word — UAX #29 words, NFKC + lowercase — ranked as in Output, first 10).
**Start of a project (`brief --stage start`, also injected at session start while `project.stage: "new"`):**
- the **launch definition of done** for the declared `project.kinds`: the P0/P1 rules that will apply at launch, grouped by pack, sorted by pack key then rule id, ≤ 60 lines; when the list is longer, line 60 is `… <n> more rules (shipgate brief --stage start --full)`, and `--full` prints every line;
- the **required pages** of TR-112 (the pages applicable rules require for the declared kinds and jurisdictions), each with its rule ids;
- the **Operator inputs still missing**, one line `<input> — <rule ids>` per input, sorted by input: (a) every `appliesTo.requires` policy key path (03 § 5) of a rule in the launch list that is absent from the signed policy; (b) every `business.json` key (03 § 14) that a required-facts or facts-oracle rule of § 1.2 in the launch list reads for the declared `project.kinds` and `privacy.jurisdictions`, when absent (or `business.json` itself when the file is absent); (c) `quality/data/legacy-urls.txt` when a signed `refactor.json` names a baseline whose manifest has a non-null `remote` (03 § 11–12) and the file is absent; (d) for each `journey` value (03 § 10) that a launch-list rule needs a flow for (UX-001 form and `checkout`/`signup` journeys, SEC-018 `login`, SEC-028 `logout`, SEC-067 `signup`), `quality/flows/` holding no flow with that `journey`; (e) the released contract of each service with an `api` surface when `quality/contracts/released/<service>/` is empty; (f) `hosts[]` purpose `analytics` (03 § 3.3; the analytics processor PRV-031 reads) when the privacy pack is enabled and no `hosts[]` entry has that purpose, printed as "no analytics processor declared (none is a valid answer)". An input that exists is not listed;
- the **foundation recipes** for the detected adapters: fix-hint snippets for security headers, the consent loader, error pages, the health endpoint, robots/sitemap and the form handler. These are hints the agent applies; shipgate never writes them (TR-104). Recipes are ruleset files `recipes/<adapter id>.json`: `{ formatVersion, recipes: [{ id: "headers"|"consent-loader"|"error-pages"|"health-endpoint"|"robots-sitemap"|"form-handler", title, files: [path pattern], snippet: string }] }`; the brief prints every recipe of the detected adapters, `title` plus `snippet`, in `id` order. An adapter without a recipe file prints none and the brief says so.

### 7.1 File roles
Adapter `fileRoles` patterns first (e.g. Next: `app/**/page.*` → route, `app/**/route.*` → api-handler, `app/**/layout.*` → layout), then generic defaults: `**/*.{test,spec}.*`, `**/__tests__/**`, `tests/**`, `test/**` → test; migrations dir → migration; `**/*.{css,scss,sass,less}` → style; `quality/data/**` → data; config → `*.config.*`, `tsconfig*.json`, `jsconfig*.json`, `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `composer.json`, `Gemfile`, `requirements*.txt`, `vercel.json`, `netlify.toml`, `wrangler.toml`, `Dockerfile`; asset → extensions `png jpg jpeg gif webp avif svg ico bmp woff woff2 ttf otf eot`; component → remaining source files under a *route root* (the literal prefix, before the first glob character, of each adapter `fileRoles` pattern with role `route`); else `source`. The first matching pattern in this order wins.

## 8. `check`, stop, detached verify, budgets

| Mode | Budget | Runs |
|---|---|---|
| `pre` | ≤ 300 ms, no toolchain/network | protected paths/keys, sensitive paths, role write scopes, command policy (§ 8.2), Operator-command gating |
| `post` | ≤ `timeBudgets.check` (10 s) | lock (mtime+size cache), diff rules, `ast` rules on changed files, `graph` rules on the reverse-import closure (≤ 2,000 files; else deferred), data validation if data changed, brief injection |
| `stop` | ≤ min(`timeBudgets.stop`, host timeout − 5 s); in practice < 2 s | reads the **sealed verdict record** (§ 8.1) |
| `verify --changed` | ≤ `timeBudgets.verify` | G0–G2; G3 for affected services; G4/G6 on *affected routes* and flows touching them → at most `PARTIAL` (FAIL/BLOCKED reported as is). Affected routes: routes whose route file changed or lies in the reverse-import closure of a changed file (the `post` graph); a changed `style`, `data` or `config` file (§ 7.1) affects every route of its service. A flow touches them when one of its step URLs is on an affected route. An affected service is one owning a changed file. G5: only for the programmatic families whose `quality/data/` files, family keys or route files changed, on their pages (all other content rules `skipped(scope)`); G7: only when `--against` or an implied baseline (§ 1.6) applies, on the affected routes; G8: `SKIPPED(scope)`; G9: consumed for the `auditTargets` (03 § 17) that are changed files or whose route group is affected. Every part not run is `SKIPPED(scope)` or `skipped(scope)` |
| `verify` | ≤ `timeBudgets.verify`; rules with `profile: nightly` only under `--profile nightly` | everything |

When a `check` mode exceeds its budget, its unfinished checks (including `graph` rules over the 2,000-file closure limit, "deferred") are `skipped(deferred)`, listed in the output, and run in the next `verify`; they never count as passed. `pre` never skips the protected-path and command-policy checks: if they can't finish within 300 ms, the call is denied.

**Budget exhaustion** (DECISIONS D-001): gates not finished when the budget runs out are `BLOCKED(budget)`. Owner is `operator` (raise the budget or move rules to the nightly profile) only when the state dir holds no earlier `verify` on the same lock digest that finished those gates, or the last such run used ≥ 90 % of `timeBudgets.verify`. Otherwise the tree change made the run slower: owner is `builder`, § 1.6 step 1 treats the gate like a BLD failure (base `FAIL`), and there is no handoff. The report lists each unfinished gate's duration in both runs. A project command that exceeds its own `timeoutSec` (03 § 3.2 `commands`) is killed with its process tree and is a builder-owned `command-failed` finding of BLD-001…BLD-005, never `BLOCKED(budget)`.

**Detached runs:** `verify --detach` starts a background job and returns its id immediately; `status --wait [--timeout <s>]` blocks until done or timeout and prints the summary. Agents use these so long runs never exceed shell-tool timeouts.

### 8.1 Sealed verdict record and stop rules
- The tree hash is computed **before G1**. An untracked, non-ignored path enters `<state dir>/shipgate/<repo-id>/generated.json` only when it did not exist before G3 started in this run, exists after G3, and matches the adapter's `generatedPatterns` (03 § 6) or the built-in list `next-env.d.ts`, `**/*.tsbuildinfo`, `.next/**`, `dist/**`, `build/**`, `target/**`, and `**/*.d.ts` under the adapter's build output directory; it is reported as W (`generated-file-not-ignored`). Other untracked files that G3 creates or changes stay in the hash and are reported as W `generated-file-not-ignored` too. Each listed path's post-G3 content hash is recorded with it; a listed path whose content before G3 of a later run differs from that recorded hash is removed from the list (it was edited outside the build) and reported as W. treeHash (§ 15) excludes every path in the list, everywhere it is computed (sealing, stop hook, attempts). When G3 adds a path, the run's treeHash is recomputed without it before sealing. Tracked files are never added to the list: a tracked file that G3 changes is reported as W (`build-modified-tracked-file`) and stays in the hash.
- At the end of every `verify`, shipgate writes `<state dir>/shipgate/<repo-id>/verdicts/<treeHash>.json`: `{ treeHash, verdict, reportDigest, handoff, createdAt }` plus an HMAC-SHA256 with the per-install secret (03 § 7.1). Report files in `quality/out/` are for humans and tools; **the stop hook trusts only the sealed record**.
- **Stop is allowed when** the sealed record matches the current tree hash and either the verdict is `PASS` (from a full, non-PARTIAL run), or a Verifier-written handoff exists (reasons and conditions: 04 § 1.9).
- Otherwise stop is blocked with: "Run `shipgate verify --detach`, then `shipgate status --wait`, and fix the findings."
- Loop guard: after **3** consecutive blocked stops in the same agent session with an unchanged tree hash and no new verify, shipgate writes an `unverified-stop` handoff and allows the stop; the next `verify` and CI report it prominently as W, and AGT-007 counts it in the session summary.
- Break-glass: a `verify` that finds a valid Operator-signed `quality/out/break-glass.sig` (03 § 15) for its tree hash, before its `expiresAt`, seals a `break-glass` handoff and records the signature's `nonce` in the state dir. The stop hook allows the first stop for that record and marks the nonce used; a second stop, or a record whose nonce is used, is blocked again.
- Honest limit: the install secret has no passphrase, so a process running as the same user could forge a sealed record locally; CI (which recomputes the verdict) is authoritative, exactly as for the lock (01 § 5.3).

### 8.2 Command policy evaluation
1. Tokenise per shell (bash, PowerShell, cmd); split pipelines, chains, subshells.
2. Resolve one level of indirection: package-manager scripts (`npm|pnpm|yarn|bun run <name>`, `npx <bin>` of known deploy tools) to their script bodies; `make <target>` to its recipe when a Makefile is present; `bash|sh|pwsh -c "<string>"` to the inner command.
3. Match each simple command against the built-in deny list (05 § 3.2) and the policy's `commandPolicy`.
4. Commands containing dynamic expansion (`$(…)`, backticks, `eval`, `Invoke-Expression`) whose literal text contains a denied token are denied.
5. Remaining gap (scripts written to files and executed later, compiled binaries): the post-hook diff and CI are the backstop; the report states it.

## 9. Findings: grouping, fingerprints, attempts

### 9.1 Failure classes (normative taxonomy)
`status-mismatch`, `redirect-chain`, `redirect-target`, `missing-element`, `duplicate-element`, `value-mismatch`, `forbidden-value`, `missing-header`, `header-value`, `leak`, `parse-error`, `budget-exceeded`, `access-allowed`, `access-denied-wrongly`, `schema-violation`, `contract-violation`, `diff-violation`, `pattern-match`, `cycle`, `orphan`, `inconsistent-set`, `similarity`, `skeleton-mismatch`, `visual-diff`, `flow-step-failed`, `runtime-error`, `vulnerability`, `licence`, `stale`, `quarantine-rate`, `command-failed`. Each rule's metadata lists the classes it can emit.

### 9.2 groupKey
| Channel | groupKey |
|---|---|
| http, html, site | rule + route pattern + failure class |
| ast, graph | rule + file + pattern id |
| content | rule + family / route group |
| browser, PRF-\* budget parts | rule + route group + metric |
| browser, every other rule | rule + route group + check id, where check id = the axe rule id for axe findings, flow id + step index for flow findings, otherwise the detector's check name listed in the rule text (the part name when it lists none) |
| deps | rule + package + advisory |
| data | rule + family + field |
| db | rule + migration file / table |
| contract, baseline | rule + endpoint/route pattern + diff path |
| cfg, lock, diff, build | rule + path / command |
| cmd | rule + service + command |
| edge | as `http` |
| hook | rule + session + tool |
| review | rule + review target |

**Serialisation.** A groupKey is the string of the rule's metadata `groupKey` components (03 § 5; by default the table's components for the rule's first channel, without `rule`), in that order, each rendered as: `routePattern`, `routeGroup` = `<service id>:<pattern or group id>`; `file`, `path` = repo-relative path with `/` separators; `endpoint` = `<METHOD> <service id>:<path pattern>`; `diffPath` = JSON Pointer; `locale` = `locale:<tag>` (§ 15 *Page locale*); every other component = its value verbatim. Components are joined with `|` (a `|` inside a value is written `%7C`); when the finding's part is not `main`, a final component `#<part>` is appended. The rule id is never part of the string; a finding is identified by rule + groupKey. Two services never share a groupKey: when no component is service-qualified (`routePattern`, `routeGroup`, `endpoint`), the string is prefixed `<service id>:`. Example (03 § 17): `web:/api/invoices/{id}|access-allowed`. locationKeys (§ 9.3) are serialised the same way. The *merge key* (§ 9.4 Dedupe) is the groupKey string without its `|#<part>` component.

### 9.3 Debt location keys and matching
| Channel | locationKey |
|---|---|
| ast | file + enclosing symbol path + pattern id + occurrence index within the symbol |
| graph | rule + cycle member set (sorted) / import edge |
| http, html, site | route pattern + failure class |
| browser | route group + check id + normalised selector (axe) / flow id + step |
| content | family / route group + failure class |
| data | family + field + failure class |
| db | migration file + statement index / table + policy |
| deps | package@major + advisory |
| contract, baseline | endpoint + diff path |
| cfg, diff, build, lock | rule + path |
| cmd | rule + service + command; `occurrences` = diagnostics counted with the adapter's `diagnosticPatterns` (default 1) |
| hook, review | not debt-eligible (metadata validation rejects debt entries for them) |
| diff (SEC-050 `history`) | path + `@` + first commit containing it + `#` + pattern id + `#` + first 12 hex of the value's SHA-256 |
| edge | as `http` |

Each debt item records `occurrences`; a higher count for the same key is a new finding. File renames are followed with git rename detection (similarity ≥ 50 %).

### 9.4 evidenceHash, dedupe, ranking
- Every groupKey (§ 9.2) and locationKey (§ 9.3) carries the finding's `part` (§ 1.8; the `#<part>` component of § 9.2 *Serialisation*). Findings of different parts, and so different severities, never merge, except by `owns` (Dedupe below), and W debt can't hide a P0 part.
- `evidenceHash` = SHA-256 of JCS `{ rule, part, groupKey, targets, actual }`. `targets` = the `target` strings of the finding's examples (03 § 17), sorted bytewise, first 50. `actual` = the examples' `actual` strings with these substrings removed: the run's probe nonces (§ 15 *Lock-digest PRNG*, *Values*); ISO 8601 and RFC 7231 date-times; UUIDs; values of the response headers `X-Request-Id`, `X-Correlation-Id`, `Traceparent`, `CF-Ray` and `X-Amzn-Trace-Id`; and every integer that is the quantity of items found (the finding's `count`, which is not hashed). Numbers with a unit of time are rounded to 100 ms, CLS values and ratios or fractions to 0.01, byte sizes to 1 KB, every other number kept; the strings are then sorted bytewise and de-duplicated. Wall-clock outcomes never enter it (01 § 5.4).
- Dedupe: a finding of an owned rule (or owned part, `RULE#part`, listed in another rule's `owns`) merges when the owner has a finding with the same merge key (§ 9.2 *Serialisation*: the groupKey string without its part component) and the same service; the part of the owned finding and the part of the owner's finding may differ, and the merged finding keeps the owner's part. A finding is absorbed only when its severity is not higher than the owner finding's severity (P0 > P1 > P2 > W); otherwise it stays separate under its own rule and part. An absorbed finding with status `blocking` makes the owner finding `blocking`. The owner's finding keeps its rule, part and severity, adds the absorbed examples to `examples` and `count`, and lists the absorbed rule ids in `absorbed` (03 § 17). When the owner has no such finding, the absorbed finding is reported under its own rule. A finding of a rule (or part) that is not in the owner's `owns` list never merges. An owner never has a weaker waivability than what it absorbs (metadata validation rejects that).
- Ranking: severity → owner (`builder` first) → gate → rule id → groupKey.

### 9.5 Repair attempts
An **attempt** for a finding = a `verify` run on a tree whose diff from the previous run that reported the finding touches the finding's `fixLocation`, or, when it has none, changes a file that affects the finding's route group or file under the § 8 `verify --changed` mapping (the file itself, a file it imports transitively, or a `style`/`data`/`config` file of its service). Other tree changes don't count. A finding becomes `exhausted` when its evidenceHash survives 2 attempts, or its groupKey survives 3 attempts (P2 budget findings use groupKey only, since bucketed values drift). A run counts as an attempt only if the finding's rule was evaluated in it. A finding that isn't reported by a run that evaluated its rule is cleared, with its counters. Attempts are stored in the user state dir.

## 10. Crawl, discovery, sampling, route groups

- **Seeds:** `/`, sitemaps (robots `Sitemap:` + `/sitemap.xml`), declared static paths, adapter routes (params from inventory rows, fixtures, then the value `1` for a param whose pattern regex (03 § 2.1 `{name:regex}`) matches `1` but not `sg-1`, else `sg-1`; a route whose only seed is that value and answers 404 is dropped as a seed), inventory pages.
- **Normalisation:** service case/trailing-slash policy, drop fragments and the query params matching `web-delivery.trackingParams`, sort remaining query params.
- **Extraction:** `a[href]`, `area[href]`, `link[rel=canonical|alternate|next|prev]`, sitemap `<loc>`, redirect `Location`; same-origin after mapping. Each crawled URL records the first page, in crawl order, from whose `a[href]` it was extracted (none for seeds); SE-129 uses it as the origin page.
- **Traps:** ≤ 3 query params per URL, ≤ 50 values per param per path pattern, depth ≤ 20, ≤ `crawl.maxUrls` (default 200,000) local, ≤ `crawl.remoteMaxUrls` (default 3,000) remote. Depth = link hops from a seed. A path whose segments repeat a 1–3-segment sequence ≥ 3 times consecutively is also dropped (limit `loop`). On local services the crawl ignores robots.txt `Disallow`; on remote origins it obeys the robots.txt group for shipgate's user agent (§ 6.1), else `*` (§ 15 *robots.txt evaluation*), and a disallowed URL is dropped with limit `robots`. Each URL dropped by a trap limit is recorded with the limit it hit (`params`, `values`, `depth`, `maxurls`, `loop`, `robots`), its path pattern, and the page and `a[href]` (with its `rel`) it was discovered from; programmatic CRW-004 reports them.
- **Complete crawl:** the BFS frontier emptied, no URL was dropped by a trap limit above other than URLs that were discovered only through `a[href]` elements with `rel~=nofollow` and URLs that the service's robots.txt disallows for Googlebot (§ 15 *robots.txt evaluation*), and no fetch ended in a network error or timeout after one retry. Dropped and failed URLs are listed in the report with the limit or error. Sampling doesn't affect completeness. G5's prerequisite "G4 crawl completed" (§ 1.5) means the crawl ran to its end, complete or not; an incomplete crawl is handled by `skipped(incomplete-crawl)` (Graph rules, below).
- **Order:** BFS, frontier sorted lexicographically per depth. Concurrency 16 local; remote 2 req/s (or lower `Crawl-delay`), GET/HEAD only — one exception: SEC-071's `POST /xmlrpc.php` `system.listMethods` call (read-only, `remote: read`).
- **Route groups:** adapter route patterns; else path clustering: take the normalised paths (service mount prefix removed) of the service's crawled URLs answering 200 `text/html`; process segment positions left to right; for each distinct prefix of already-rewritten segments, when the distinct values of the next segment (case-sensitive, after the normalisation above) number more than 20, rewrite that segment to `{param}` in every path with that prefix. A URL's pattern is its rewritten path; a segment with 20 or fewer distinct values under its prefix stays literal. Then split by the *route-group skeleton*: the generic `<main>` skeleton hash (§ 11) of the tree cut so that nodes at depth ≤ 3 are kept (`<main>` is depth 0), with each run of adjacent siblings whose serialisations are equal collapsed into one. Group id = the pattern, plus `#<first 8 hex of the skeleton hash>` when the pattern splits; `performance.routes` keys and groupKeys match the pattern part.
- **Sampling** (above 50,000 indexable pages (§ 15 *Indexable page*), remote mode, and browser gates): lock-digest PRNG (§ 15); strata service × surface × family/route group × locale; exactly min(1,000, family size) per family for HTTP (remote: the same per-family share of `crawl.remoteMaxUrls` as the family's share of discovered URLs, rounded down, at least 1); a route group that no programmatic family covers counts as a family for this rule (min(1,000, group size) URLs for HTTP; remote: the group's share of `crawl.remoteMaxUrls`, computed as for a family, at least 1); exactly min(3, group size) per route group for browser; plus always every `programmatic.hubs` page, declared path, fixture page and flow page. Within a family or route group, picks are spread round-robin over its strata in lexicographic order, as for fixed-size samples.
- **HTTP sample** and **browser-sampled pages** (the only definitions; every rule saying "HTTP sample (04 § 10)" or "browser-sampled" uses them). The HTTP sample is the set of crawled `public`-surface URLs answering 200 `text/html` kept by the HTTP stratum of the Sampling rule above (all of them when the run is local and there are at most 50,000 indexable pages). Browser-sampled pages are the picks of the Sampling rule's browser stratum (min(3, group size) per route group, plus the always-included pages).
- **Fixed-size samples.** An *N-URL sample per surface* (named, e.g. `preview-20`, `comparison-10`) is drawn from the surface's crawled URLs answering 200 `text/html`, indexable ones (§ 15 *Indexable page*) first. Route groups are visited in lexicographic order of their pattern, round-robin, taking per round from each group its lowest-ranked unpicked URL (lock-digest PRNG, stream id = sample name), until N URLs are picked or the pool is empty; indexable URLs are exhausted before non-indexable ones are taken. An *N-route sample* (e.g. `fault-20`) is drawn the same way but takes at most one URL per route group. A URL's *position* in the sample is the order in which it was picked. Every rule naming the same sample uses the same URLs in a run; fewer eligible URLs than N → the whole pool, and the report states the size.
- **Graph rules:** inventory families use the oracle graph and verify a sample; crawl-only sites need a complete crawl, else graph rules are `skipped(incomplete-crawl)` with a warning; for P0 and P1 rules that makes the run partial (§ 1.6 step 2).
- **Discovered routes:** CFG-003 is also evaluated in G4 on crawl-discovered routes.

## 11. Programmatic algorithms

**Formatting (inventory mode):** ICU4X, pinned CLDR version in the report. Field `format`: numbers `{ style: decimal|percent|unit, unit?, minFrac, maxFrac, grouping }`; money `{ display: symbol|narrowSymbol|code|name, minFrac?, maxFrac? }` (defaults from ISO 4217 digits); dates `{ dateStyle, timeStyle?, timeZone }`. Rounding half-even.

**Relations:** `nearest-by-geo` (haversine), `same-group:<field>` (by `priorityField` desc, then slug), `field-similarity:<fields>` (equal fields desc, then slug), `declared:<field>`. Ties → slug ascending (not for `declared`, which keeps listed order); self excluded. Candidate set, the `geo` field used, R = 6,371.0088 km, and `declared` order (no slug tie-break): programmatic PCF-005 *Related candidates*.

**Skeleton identity (TPL-004):**
1. Parse `<main>` (html5ever); drop comments, `<script>`, `<style>`, whitespace-only text.
2. Replace text of `data-fact` / `data-token` elements with `⟦name⟧`.
3. Mask values of `href`, `src`, `srcset`, `alt`, `title`, `aria-label`, `data-value`, `datetime`, `content`.
4. Replace all children of each `data-list` container with a single `⟦list⟧` placeholder (empty and non-empty lists hash the same).
5. Detach every `data-section` element from the tree **without leaving a placeholder**. A section is *present* when its field has a value for the row. `aiText` fields that aren't reviewed (DAT-015) count as absent here, in the oracle and in the inventory.
6. **Main hash:** canonical serialisation of what remains (sorted attributes, collapsed whitespace, NFC) → SHA-256. All pages of a family/locale share one main hash, and so do all pages of a hub/locale (paginated pages included).
6a. **Section presence and order:** on each page, the detached sections are exactly the present fields, none missing and none extra. They appear in template order: the order of the family's sections in the field declaration. A violation is reported as TPL-005 (`skeleton-mismatch`).
7. **Section hashes:** each detached section is hashed with steps 2–4 and 6 applied to its own subtree. Every instance of a section name across the family/locale must have the same hash.
8. The expected main hash is the one shared by the most pages of the family/locale (or hub/locale) (ties → the hash of the lowest-slug page among the tied hashes). Every page with another hash is a `skeleton-mismatch` finding, diffed against the lowest-slug page with the expected hash; the report shows the first differing node path. Section hashes follow the same rule per section name. When the first differing node is a text node, the page is reported as TPL-006 (per-row prose) instead of TPL-004.

**Generic `<main>` skeleton hash** (§ 10 route groups, RTE-010, AEO-014 `agent-parity`): step 1; step 3; every text node replaced by `⟦t⟧` (adjacent text nodes merged first); `data-section` and `data-list` subtrees stay in place (steps 2, 4 and 5 are not applied); then the step 6 serialisation and SHA-256. TPL-004's main and section hashes (steps 1–8) are used only by TPL-004.

**Similarity (CNT-006):** row-specific text only; UAX #29 words, NFKC + lowercase, 5-shingles, MinHash 128 (permutation i of a 5-shingle = the first 8 bytes, big-endian u64, of SHA-256(be32(i) ‖ UTF-8 shingle with its words joined by U+0020), i = 0…127; the signature value i is the minimum over the text's shingles), LSH 32×4 (band k = signature rows 4k…4k+3, k = 0…31), exact Jaccard on candidates; `omit` drops the lower `priorityField` row (ties → later slug). Domain, row text and pair-resolution order: programmatic CNT-006.

**Live-mode snapshot and parse-back:** `family.snapshot { db, sql }` → JSONL (ownership and the no-source outcome: programmatic § 6 *live*). Parse-back: digits of any numbering system → ASCII; CLDR grouping/decimal separators; all space variants equal; currency by symbol/narrow symbol/code mapped to the data's ISO code; percent position free; dates against the locale's CLDR patterns at four lengths comparing Y/M/D (+ h/m). Also used by SCH-006 for prices and dates. Unparseable → fail with code points shown.

## 12. Parity, soft-404, leaks

- **Raw vs rendered (RTE-001):** token overlap of `<main>` text raw vs rendered ≥ `parity.minOverlap` on browser-sampled pages.
- **Mobile vs desktop (RTE-014):** raw `<main>` text and links under smartphone vs desktop Googlebot UAs, token overlap (reference: desktop) ≥ `parity.mobileMinOverlap`; head metadata (title, description, robots, canonical, hreflang pairs, JSON-LD `@type` set) compared for equality.
- **Token overlap** (the only definition; RTE-001, RTE-014, IDX-013, RES-003, and every rule citing "04 § 12 token overlap"): text is NFKC-normalised, full Unicode case-folded and split into UAX #29 words; punctuation-only tokens are dropped. Overlap = |A ∩ B| ÷ |A| over **multisets**, where A is the reference text and B the compared text. References: the rendered `<main>` for RTE-001 `main`; the desktop response's raw `<main>` for RTE-014; the page's raw-HTML `<main>` for IDX-013; the same route's no-fault response `<main>` for RES-003. Link overlap (RTE-014) uses the same formula over the multisets of `a[href]` targets in `<main>`, made absolute and canonicalised with the § 10 normalisation. A reference with 0 tokens (or 0 links) counts as overlap 1.0.
- **Soft-404:** title, H1 and the first 200 characters of `<main>` vs the page locale's (§ 15 *Page locale*) soft-404 phrase list, effective list = ruleset list ∪ policy `soft404Phrases[locale]` (the ruleset ships complete lists for 20 major locales); or near-empty `<main>` (< 50 UAX #29 words and no `data-fact` element). A match = the phrase occurs whole-word (UAX #29 word boundaries) after NFKC and case folding of both sides.
- **Leak scan (MET-008):** template markers (`{{…}}`, `{field}`, `${`, `<%=`, `%s`/`%d`, `[INSERT`, `[object Object]`) everywhere except `<code>`, `<pre>`, `<kbd>`, `<samp>`, `<script>`, `<style>`, `<template>`. The words `undefined`, `NaN`, `null`, `TODO`, `FIXME`, `TBD` only where they make up the **entire** value of: `<title>`, meta description, `og:*`, `<h1>`, an attribute value, a `data-fact`/`data-token` element, or a table cell — never in ordinary prose (filler text such as lorem ipsum is owned by MET-011 everywhere). Elements are excluded only when matched by a selector of `web-delivery.leakIgnore` (CSS selectors, signed policy, default `[]`); each excluded element is reported as W. The attribute `data-shipgate-ignore` has no effect.
- **Error leakage (SEC-007):** response bodies of error probes are scanned for stack-trace patterns (`at <fn> (<path>:<line>`, `Traceback (most recent call last)`, `Exception in`, `.php on line`, `stack:`), SQL error signatures (`SQLSTATE`, `syntax error at or near`, `You have an error in your SQL syntax`, `ORA-\d+`), absolute file paths (`/home/`, `/var/www/`, `C:\`), debug-page markers (`Werkzeug Debugger`, `You're seeing this error because you have <code>DEBUG = True</code>`, `Whoops! There was an error`, `Ignition`, `Action Controller: Exception caught`, `nextjs-original-stack-frame`, `Server Error in '/' Application`, `sf-toolbar`), and internal hostnames (`localhost`, RFC 1918 addresses).

## 13. Static analysis precision

- **Same-function data flow** (AGT-003, DB-008, RTE-010 `source-hint`): an expression originates at source S when it is S itself, or is built from an expression originating at S by `await`, parentheses, type assertions or casts, destructuring, member or index access, optional chaining, or a method call on it; or it is an identifier whose every assignment in the same function is such an expression. Passing the value as an argument to another call, returning it, or storing it in a field ends the flow. (Request-derived data flow, below, is a different, wider definition.)
- **AGT-003:** non-null assertions/unwraps on values whose origin (§ 13 *Same-function data flow*) is an adapter-declared source (HTTP client responses, JSON parse, request params/body, DB results, env reads).
- **DB-008:** a `queryApis` call whose nearest enclosing loop in the same function — `for`, `for…of`, `for…in`, `while`, `do…while`, a Python/Ruby/Rust loop or comprehension, or a callback passed to `map`, `forEach`, `flatMap`, `reduce` or `each` (including `Promise.all(x.map(…))`) — iterates a value whose origin (§ 13 *Same-function data flow*) is the result of another `queryApis` call; calls reached only through a callee are not followed.

## 14. False-positive governance and rulesets

- Every rule starts `experimental` and becomes `stable` when its corpus passes: ≥ 3 known-good projects (synthetic per-adapter fixture apps count) with zero findings and ≥ 1 known-bad fixture per failure class detected. A **launch-stable list** in the first ruleset names the rules that ship stable on day one.
- `shipgate report-fp <evidenceHash>` packages a redacted repro (never sent automatically).
- `policy.ruleOverrides`: `off` and `warn` for non-† rules; for `†` rules only `warn`, with `expires` ≤ 14 days and a mandatory `fpReport` (the `report-fp` hash), printed on every report while active. `experimental-on` makes an experimental rule block at its declared severity.
- Vendor hotfix rulesets (`YYYY.MM.N`) can set a rule's lifecycle to `experimental` or lower its severity to `W`; they cannot change a `†` flag or raise anything. Projects adopt them by bumping `ruleset`.
- A finding whose fix lies outside the Builder's owned paths (`fixLocation`) is reassigned to owner `operator`.
- The binary embeds the current ruleset and the 3 previous ones.
- **Per-locale ruleset files** (e.g. `stop-words.json`, `verbs.json`, `advice-patterns.json`, `clickbait-patterns.json`) are JSON objects keyed by BCP 47 tag. Lookup of a page's entry and the outcome when the locale has none: § 15 *Page locale* (the only definition; no silent `en` fallback). A file whose rule text defines another key (e.g. `postal-patterns.json` by ISO 3166-1 country) uses that key; the § 15 lookup and no-entry outcome don't apply to it.

## 15. Supplementary definitions

- **treeHash:** SHA-256 over the lines `path\0<lowercase hex SHA-256 of the file>\n`, sorted bytewise by UTF-8 path, for the files listed by `git ls-files -z --cached --others --exclude-standard` run with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` pointing at an empty file (so machine-wide excludes don't change the set). Files listed but absent on disk are skipped; a symlink hashes its target string; a submodule hashes its commit id. Without git: every regular file under the worktree root except `.git/`, `node_modules/` and `quality/out/`. Per-file hashes follow 03 § 1 *File hashes* (BOM and CRLF normalisation for text files). Paths are relative to the worktree root with `/` separators, UTF-8, as git prints them (without git, as read from the filesystem, no case folding). Computed before G1; excludes the paths in `generated.json` (§ 8.1).
- **Lock-digest PRNG** (the only definition; 01 TR-103 and every "PRNG seeded with the lock digest" in the spec use it; no ChaCha stream or shuffle is used). *Draws:* to choose from a set of candidates, each candidate is ranked by SHA-256(the 32 raw bytes of the lock digest, i.e. the hex after `sha256:` decoded ‖ `0x00` ‖ UTF-8 stream id ‖ `0x00` ‖ UTF-8 candidate key) ascending, bytes compared as unsigned; a draw takes candidates in rank order, so choosing n of N takes the first n. The candidate key is the normalised URL (§ 10) for URLs and the identifier otherwise (variable name, target id, route-group id, changed-file path, sitemap `<loc>`). The stream id is the sample or use-site name (`preview-20`, `comparison-10`, `fault-20`, `host-unsupported`, `audit-targets`, `IDX-011`, `OPS-010`; § 10 sampling: `sample:<service>:<surface>:<stratum>`, where `<stratum>` = `<family key or route-group id>#<locale tag>`, the locale tag as in *Page locale* and `-` for a stratum with no locale); omitted means the rule id. *Values:* where a rule needs values rather than a choice (SEC-030 fuzz values, probe nonces), value k (k = 0, 1, …) of stream s is the first 8 bytes of SHA-256(the 32 raw lock-digest bytes ‖ `0x00` ‖ UTF-8 s ‖ `0x00` ‖ k in decimal ASCII) read as a big-endian u64; a nonce is the lowercase hex of value k, zero-padded to 16 digits (the security pack's `{n}` takes its first 8 characters, security shared definitions *Nonce*).
- **repo-id:** first 16 hex characters of SHA-256 of the UTF-8 bytes of the worktree root path from `std::fs::canonicalize`, with a leading `\\?\` removed, the drive letter upper-cased, `\` replaced by `/` and no trailing `/` (each git worktree is its own repo-id).
- **Reference time:** rules that depend on "now" (SE-104 news recency, SE-108 expiry, freshness warnings) use the HEAD commit time (or `dataAsOf` for data rules), never the wall clock, so reports stay deterministic. HEAD commit time = the committer date (`git log -1 --format=%cI HEAD`); without git or without a commit it is the wall clock at run start, and the results that depend on it are marked non-deterministic. Exceptions: every observation made in the edge pass (G8), plus LNK-006/007, depends on live systems. Those that are time-based (SEC-015 `Expires`, SEC-056 certificate validity, SEC-059, IDX-011) use the wall clock. All of these results are marked non-deterministic in the report and are excluded from the determinism tests. Date comparisons that gate verification (expiries, activation dates, "already happened" dates) use the expiry clock of 01 § 5.4, which combines the reference time with the wall clock; UX-020 part `timer` reads the wall clock directly. Both are non-deterministic (TR-103).
- **E.164 normalisation:** libphonenumber metadata from the toolchain. The default region is the country of the business-facts location the page belongs to (`pagePath`), else the region of `defaultLocale`, else none (the number must be in international format).
- **robots.txt evaluation:** RFC 9309. Use the most specific matching user-agent group, or the `*` group if none matches. Allow/Disallow resolve by longest match, with Allow winning ties. `$` and `*` wildcards are supported. Engine-specific groups don't inherit from `*`. Used by § 10 (crawl), AEO-002, CRW-004, IDX-004, IDX-008, IDX-009, IDX-011, MET-014, SCH-004 (`Organization` `logo`), SCH-009, SE-002, SE-010 (auxiliary tokens with `fallbackTokens`: search-engines SE-010 *Token decision*), SE-011, SE-132 and SE-301.
- **Indexable page** (the only definition; every rule, sample and pack that says "indexable" uses it, and "indexable canonical" and "indexable URL" mean the same set). A URL is an indexable page when all hold:
  1. it is on a `public` surface of a service and is a crawled URL or an inventory page (§ 10 seeds);
  2. when requested it answers 200 with `Content-Type` `text/html`, without a redirect (inventory pages not requested in a sampled run are taken to);
  3. the Operator's configuration marks it indexed: for a programmatic family page, the family has `indexation: "index"` (programmatic § 1.3), the page is a released eligible page (programmatic § 4-0, CNT-001) and its row is not served `noindex` by DAT-017 `onLow: "noindex"`; for a hub page, the hub has `indexation: "index"` and is generated (PCF-007 `minMembers` over released eligible rows), every page up to its inventory `pages` included; for any other URL, the most specific matching `web-delivery.indexRules` entry (03 § 2.1 specificity) has `index: true`, where `web-delivery.staticPaths[]` entries and `privacy.legalPages` values count as exact-path entries with their `index` value (ties: WCF-006); no matching entry → indexed;
  4. it matches none of `web-delivery.retired[].path`, `search-engines.products.discontinued[].pattern`, `web-delivery.syndicated[].pattern` or an `older` pattern of `web-delivery.docs.versions`, is not an internal site-search URL (IDX-012) and is on no alias host (URL-011);
  5. its query, after § 10 normalisation, is empty or consists only of: the `param` of a matching `web-delivery.pagination` entry, or the `pagination.param` of a `programmatic.hubs[]` entry whose `pagination.style` is `"query"` on that hub's pages, with a value ≥ 2; the `param` of a matching `web-delivery.contentParams` entry with mode `self-canonical`; a parameter set listed in `search-engines.facets.indexable`; `search-engines.products.variantParams` parameters on a variant URL that is self-canonical under SE-111.

  Only these Operator-owned inputs and shipgate's own request decide, with one exception: item 5's variant clause, where SE-111 lets the page choose between self-canonical variant URLs (indexable) and variant URLs canonical to their `ProductGroup` page (not indexable); SE-111 fails a mixed choice. Apart from that, nothing on the page takes a URL out of the set: a `noindex` directive, an `X-Robots-Tag`, a robots.txt disallow or a canonical to another URL never removes it; on an indexable page they are findings of MET-006, IDX-004 and URL-004. A URL that item 3 marks indexed but that answers non-200 or redirects is judged by RTE-004 (status table), URL-002 and LNK-002. The expected canonical of an indexable page is its own canonical form (URL-001).
- **Page locale** (the only definition; every rule that says "page locale", "the locale's …" or "per locale" uses it). The page locale of a response on service s is: with `web-delivery.localePrefix: "always"`, the `web-delivery.locales` entry whose locale segment (web-delivery § 1) equals, case-insensitively, the first path segment after s's mount (none matches → `web-delivery.defaultLocale`); with `"never"`, `web-delivery.defaultLocale`; for a programmatic family or hub page, the `locale` of its inventory line (03 § 13). When the web-delivery pack is not enabled, the page locale of every response is the tag `und`; no per-locale list has an entry for it, so every per-locale check runs under *No entry* below and names `web-delivery.defaultLocale` as the missing input. The page's `<html lang>`, `Content-Language` header, hreflang and any other agent-written markup are never used (MET-007 checks that `<html lang>` agrees).
  - **Per-locale ruleset lists** (vendor ruleset data keyed by locale, e.g. the soft-404 phrases, `stock-count-phrases`, `claimPhrases`, `ai-addressed-phrases.json`, CLDR data): looked up by the page locale's full BCP 47 tag, else by its primary language subtag. Where a policy key supplies a list for the same data (e.g. `web-delivery.soft404Phrases`), its entry for the tag or subtag counts as an entry and is merged with the ruleset entry (union). Operator-written per-locale values that aren't ruleset data (e.g. `privacy.consent.banner` labels) follow their own pack text.
  - **No entry** for the page locale (neither the ruleset nor such a policy list has one): the check is not skipped and not `notApplicable`. It runs with the `en` entry, and the rule emits one finding per (rule, locale) at the severity of the rule or part that uses the list (status `blocking` for P0–P2; `warning` for W rules and W parts, § 1.3), failure class `missing-element`, owned by `operator`, groupKey rule + `locale:<tag>` + class, naming the locale and the list. The Operator resolves it by adopting a ruleset that has the locale (§ 14), supplying the policy list where the rule has one, or removing the locale from `web-delivery.locales`. When only Operator-owned findings remain, the run ends in an `operator-owned` handoff (§ 1.9), never a PASS.
- **Swap similarity (CQ-008):**
  1. Within one route group, replace place names from the ruleset gazetteer with `⟦place⟧` (longest match, NFKC, case-folded).
  2. Find candidate pairs with MinHash/LSH (§ 11 parameters) at Jaccard ≥ 0.5 on the masked text.
  3. A pair is swap-similar when, on a word-level Myers diff, matched words plus words in substitution hunks of ≤ 3 words on each side make up ≥ 0.8 of the words of the longer text (counted in the longer text).
  4. A connected component of ≥ 5 swap-similar pages is a finding.
- **Reference year:** the calendar year of the reference time (CQ-009 and other year checks).
- **Dead control (MET-011 `dead-anchor` for `<a>` elements on public pages; UX-006 for `<a>` elements on `app` pages and all other controls):** the control is actually clicked in the control click probe (a registered listener is not enough). It is dead when, within 1 s, the click causes none of these:
  - a navigation;
  - a network request;
  - a DOM mutation outside the element;
  - focus moving to an element other than the clicked control and its descendants;
  - a dialog;
  - a change of `aria-expanded`, `aria-pressed` or `aria-selected`.

  Controls with native activation behaviour (`<summary>`, `<label>`, submit and reset buttons, `popovertarget`/`commandfor` buttons) are judged by their native effect. On public pages every `<a>` whose `href` is absent, empty, `#` or `javascript:` belongs to MET-011 `dead-anchor`, whatever its role.
- **Copyright holder (MET-011 `copyright`):** the text after `©`/`(c)`/`Copyright` and an optional year range, up to the end of the sentence or element, compared with `brand`, `siteName`, `business.json` `name`/`legalName` and `placeholderAllow`. It passes when the holder text, normalised (NFKC, case-folded, whitespace collapsed, trailing punctuation and `All rights reserved` removed), equals or starts with one of the comparison values normalised the same way.
- **Visible dates (AEO-006, AEO-012, SCH-005, mainTextHash):** `<time datetime>` elements, plus text matched by the locale's CLDR date patterns within 200 characters after the `<h1>` or inside elements whose class or id contains `date`, `updated`, `published` or `byline`.
- **Alias-host wildcards (URL-011):** an adapter's `defaultAliasHosts` entry with a wildcard is resolved from platform config: the Vercel project name in `.vercel/project.json` or `vercel.json`, the Netlify site name in `netlify.toml` or `.netlify/state.json`, the Pages project name in `wrangler.toml`. If no concrete host can be resolved, that entry is URL-011's blocking `missing-element` finding owned by `operator` (§ 1.2 required-facts rules), asking the Operator to list the concrete host in `aliasHosts`; never `notConfigured`.
- **Fallback body (SEC-034):** the response to the non-existent path `/sg-{n}<ext>` (`{n}` = the first 8 hex characters of SHA-256(the 32 raw lock-digest bytes ‖ `0x00` ‖ `sg-probe`), as in *Lock-digest PRNG*; the same `{n}` as the RTE-004 Unknown-URL probe), normalised by removing ISO 8601 and RFC 7231 dates, UUIDs, and runs of ≥ 16 `[A-Za-z0-9_-]` characters containing a digit, then hashed. A probe response with the same masked hash is a fallback, not an exposed file.
- **No side effect:** before and after the probe, shipgate compares the row count and the hash of rows (excluding columns named `updated_at`, `updatedAt`, `modified_at`, `modifiedAt`, `last_seen_at`, `lastSeenAt`, `last_login_at`, `lastLoginAt`, and timestamp columns the adapter declares) of every table the seeded database contains. Any difference is a side effect. Captured emails and egress requests are compared too.
- **Default `remote` metadata:** rules whose channels are only GET/HEAD-capable (`http`, `html`, `site`, `content`, `browser`, `edge`) default to `read`; rules that send writes, login attempts, fuzzing, load or faults declare `write`; `ast`, `graph`, `diff`, `deps`, `cmd`, `data`, `db`, `build` are `none` for remote services. `contract` counts as GET/HEAD-capable; `cfg`, `lock`, `hook`, `baseline` and `review` are ignored when choosing the default, and a rule with only these channels is `none`. Without any declaration: every rule or part whose text says "(mutating stage, 04 § 4.2 step 8)", every fault rule (RTE-007, RES-\*) and TST-001…TST-010 are `write`; OPS-001…OPS-005 and OPS-007…OPS-014 are `none`. A part may set its own `remote` (§ 1.8); otherwise it has the rule's.
- **Default field formats (inventory mode):** `int` → decimal, grouping on, 0 fraction digits; `number` → decimal, grouping on, max 2 fraction digits; `money` → `symbol`, ISO 4217 minor digits; `date` → `medium`; `datetime` → `medium` date + `short` time in the site time zone; `bool` → localized yes/no from the ruleset; `geo` → not rendered as text (coordinates only in data attributes and JSON-LD).
- **AI-text number detection (DAT-014):** numeric tokens are runs matching the locale's CLDR number pattern (with grouping/decimal separators, optional currency symbol or percent sign); spelled-out numbers are ignored; 4-digit tokens between 1900 and 2100 are treated as years and must match a year of a date field; money values are compared in major units against `money` fields; dates are found with the locale's CLDR date patterns.
- **aiText provenance:** a field of type `aiText` implicitly declares its five sibling fields (`<f>Model`, `<f>GeneratedAt`, `<f>PromptVersion`, `<f>ReviewedBy`, `<f>ReviewedAt`); they are not unknown keys. YMYL reviewer authority = family key `ymylReviewers: [names]`.
- **Index rate (ROL-003):** `indexed URLs of the wave ÷ all URLs of the wave`; wave URLs absent from the export count as not indexed.
- **Contract request generation (API-002):** for every operation and every documented response status, one request built from the operation's examples, else from a minimal valid instance of the request schema (required fields only, first enum value, minimum lengths). Requests for a documented 2xx or 3xx status are sent as the *primary account* (the account whose id is first in byte order among `verifyEnv.auth.accounts`), or anonymously when the operation's effective `security` (operation level, else root) is absent or empty. Statuses that need special state (401, 403, 404) are produced with the anonymous account, the *other tenant's account* (the first account in byte order whose `tenant` differs from the primary account's), and a probe id. A response key that is `default` or a range (`1XX`…`5XX`) generates no request; it is listed `skipped(not-generatable)` per operation, and its schema judges any observed response whose status isn't documented by number. Other documented 4xx statuses: 400 and 422 are produced by the SEC-030 mutation "required field removed" applied to the first required field (schema order) of the minimal instance; 409, 429 and 5xx are not generated and are listed `skipped(not-generatable)` per operation and status. Requests other than GET/HEAD/OPTIONS run in a mutating stage (§ 4.2 step 8).
- **Fuzzing (SEC-030):** per operation, each mutation applied alone to the minimal valid instance (*Contract request generation*): (1) each required property removed in turn (schema order, depth-first); (2) each property replaced by a wrong JSON type — a string by `0`, a number or integer by `"x"`, a boolean by `"true"`, an array by `{}`, an object by `[]`; (3) the string property ranked lowest by the lock-digest PRNG (stream id `SEC-030`, candidate key = the property's JSON Pointer) replaced by 10,240 characters `a`; (4) the extra top-level property `sg_unknown` = `1` added (skipped when the schema allows additional properties). Expected: 400 or 422 with the error shape (API-003).
- **Facet probes (SE-130/131):** against each facet probe base (search-engines § 3.3: the first 3 URLs in crawl order matching each `facets.routes` pattern, else the first 3 crawled URLs carrying a `facets.params` parameter), for each `facets.params` entry, a request with the value `shipgate-none` (expected 404), a request with parameters in reversed order and one with a default value from `facets.defaults` (both expected to redirect once to the normalised URL).
- **Hidden content** (CNT-009, SE-109, SE-123, AEO-014, SEC-055 honeypot fields (items 1–6, applied to form fields whatever their text) and any rule that says "hidden" — the only definition; packs reference this item and don't list their own). Judged in the rendered DOM 2 s after `load` (Playwright, computed styles), at the `mobile` and the `desktop` viewport of 03 § 10 (an element hidden at either viewport is hidden) unless the rule names one viewport. An element with non-whitespace text, or a link, is *hidden* when any of these holds:
  1. it or an ancestor has the `hidden` attribute, or `aria-hidden="true"`;
  2. computed `display: none` or `content-visibility: hidden` on it or an ancestor; computed `visibility: hidden` or `collapse` on it;
  3. the product of computed `opacity` over it and its ancestors is < 0.05;
  4. computed `font-size` < 2 px;
  5. **clipped to ≤ 1 × 1 px:** its visible box — the bounding client rect intersected with every ancestor that clips (`overflow` other than `visible`, `clip`, `clip-path`) and with its own `clip`/`clip-path` — is at most 1 px wide and 1 px high (covers zero width/height with overflow hidden, `clip: rect(0 0 0 0)` and "sr-only" patterns);
  6. **wholly outside the page box:** its bounding rect — for text moved by `text-indent` or padding, the union of its text nodes' `Range` client rects — lies entirely left of x = 0, above y = 0, right of the document element's `scrollWidth` or below its `scrollHeight`;
  7. **same colour:** the contrast ratio (WCAG 2.2 relative luminance) between its computed text colour, alpha-composited, and its background < 1.1. The background is the median pixel colour of the element's text box in a screenshot taken with the element's text colour set to `transparent` (so background images, gradients, media and overlapping elements count; no other colour-difference test, e.g. ΔE, is used).

  Text inside an element that meets the **disclosure exemption** below is not hidden. A rule that applies this definition without the exemption says so (AEO-014 `ai-addressed`). Each rule states which elements it checks (e.g. CNT-009 required facts and main text, SE-123 links).
- **Disclosure exemption** (CNT-009, AEO-014, and any rule exempting user-revealable content; packs reference this item and don't list their own). Content is exempt when it is:
  1. inside a closed `<details>`, other than its `<summary>`;
  2. an element referenced by `aria-controls` of a non-hidden control with `aria-expanded="false"` (disclosures, accordions, menus);
  3. a `role="tabpanel"` referenced by `aria-controls` of a non-hidden `role="tab"` with `aria-selected="false"`;
  4. a closed `<dialog>`, or a `[popover]` element not showing, that a non-hidden control opens (`commandfor`, `popovertarget`, or `aria-controls` with `aria-haspopup`);
  5. an inactive slide of a carousel (an auto-advancing region as accessibility A11-021 part `carousel` defines it, or a region matching `[aria-roledescription=carousel]` or a `carousel-markers.json` pattern) that has a non-hidden control whose accessible name has a phrase match (accessibility § 1 *Phrase match*) in `carousel-controls.json`;
  6. inside `<template>` or `<noscript>` (never rendered).

  **Verified, not trusted:** for items 1–5 shipgate activates the control once (click; for a carousel, the next-slide control up to slide-count − 1 times) and the exemption holds only when, within 1 s, the content is no longer hidden by any item of the hidden-content list. Content that stays hidden is judged as hidden. Every exemption applied is listed in the finding evidence or the report.
- **Production project refs (CFG-004):** values of `production.keyPrefixes` and Supabase project refs extracted from `production.origins`/`hosts` entries ending in `.supabase.co`.
- **CI detection:** true when shipgate's own process environment has any of these set: `CI=true`, `GITHUB_ACTIONS`, `GITLAB_CI`, `BITBUCKET_BUILD_NUMBER`, `TF_BUILD`, `CIRCLECI`, `BUILDKITE`. It decides the trust-store source (`SHIPGATE_TRUSTED_KEYS`, 03 § 7.2), `verifyEnv.reduced.where: "ci"` and `baseline --ci`. It can be spoofed on a local machine, so setting these variables is on the agent deny list (05 § 3.2) and CI itself stays authoritative.
- **Owners of BLOCKED gates:**
  - A missing toolchain, port exhaustion, a database engine failure or another environment fault has owner `operator`. The reason is `tool-error` if shipgate itself crashed, otherwise `operator-owned`, and the gate gets a handoff (§ 1.9).
  - A gate blocked by a prerequisite takes the owner of the gate that blocked it; a check `blocked(prerequisite: BLD-004|BLD-005|DB-001)` (§ 1.5) has owner `builder`.
  - A `NOT_CONFIGURED` gate is owned by `operator` only when every missing input lies outside the Builder's `writeScope` (01 § 5; e.g. the signed policy, baselines, `verify.env`); otherwise it is owned by `builder`. A gate holding both kinds is owned by `builder`.
  - `BLOCKED(budget)`: § 8 "Budget exhaustion".
  - `BLOCKED(seed-contract)`: § 4.3. Missing database extensions (§ 4.2 step 2): `builder` when a migration that requires a missing extension is changed or added in the diff, otherwise `operator`. `blocked(no-git)` and `blocked(no-base)` (§ 5): `operator`. `BLOCKED(stopped: …)` (§ 1.5): `operator`. `BLOCKED(root-container)` (§ 4.2 step 1): `operator`.
  - Any BLOCKED or NOT_CONFIGURED cause not named above has owner `operator` when it is an Operator input or the environment (no or invalid baseline for G7, licence, CFG-004, a service below `minCoverage`), and otherwise, like a `†` rule's `blocked(<reason>)` caused by a file inside the Builder's `writeScope` (e.g. an unsupported host directive, § 3), owner `builder`.
  - A `BLOCKED` gate holding causes of both owners is owned by `builder`, as a `NOT_CONFIGURED` gate holding both kinds is; when the builder-owned cause is fixed, the Operator-owned one is reported on the next run.
- **`verify --resume`:** reuses the results of gates that finished in the previous run for the same tree hash, lock and environment hash, even under `--no-cache` (except the never-cached results of § 16); the run is partial (§ 1.6 step 2), so it never is the definition-of-done run (§ 16).

## 16. Caching

Key = SHA-256 of the JCS of `{ gate, lockDigest, ruleset, verifierVersion, toolchainManifestHash, environmentHash, input, scope, profile, against, adopt }`, where `input` = the tree hash for G1 and later gates, the sorted input-file hashes for G0; `scope` = `"full"`, or the JCS of the run's scope selectors that reach this gate (sorted `--gate`, `--pack` and `--service` values, and for `--changed` the sorted affected-route and affected-service ids, § 8); `profile` = `"default"` or `"nightly"`; `against` = for G7 the baseline id (`--against` or the implied baseline, § 1.6) plus the SHA-256 of its `manifest.json` (03 § 12), else `null`; `adopt` = whether `--adopt` was given. A result computed under a `scope` other than `"full"` is stored under its own key and never satisfies a `"full"` key. A gate whose status is `SKIPPED(scope)`, or whose stages did not all run, is never cached. Stored in `quality/out/cache/<gate>/`. Never reused across lock changes. `--no-cache` for base-branch CI (05 § 5). Outcomes that depend on the wall clock (01 § 5.4 expiry clock, UX-020 `timer`) are recomputed on every run and never served from the cache. So are every G8 gate result, LNK-006/007 results and every check against a remote service (`url`, `previewUrl`, `production.origins`): they observe live systems that change without any tree change.

- **Environment hash** (DECISIONS D-002) = SHA-256 of JCS `{ os, arch, verifyEnvSha256, env: the environment of every service, resolved, with each port number shipgate allocated for this run replaced by the token `{port}` wherever it occurs in a value (e.g. `PORT`, `SITE_URL`, database URLs), each per-run temporary directory path (embedded database data dirs, `SHIPGATE_INVENTORY_DIR`) replaced by `{tmpdir}`, and secret values replaced by their SHA-256, browserVersions, databaseEngineVersions, ci: CI detection (§ 15) }`.
- **Definition-of-done run** (DECISIONS D-002) = any `verify` with no partial cause (§ 1.6 step 2); only it can seal a `PASS` (§ 8.1). It ignores `--resume`, and its keys always have `scope: "full"`. It reuses a cached gate result only when that result's key above equals the key this run computes, environment hash included (report `gates[].cache: hit`, 03 § 17), so a sealed `PASS` is never built from cached gate results of a different environment hash.
